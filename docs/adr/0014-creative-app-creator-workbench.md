# ADR-0014: 个人创意创作台（AI 生成主流程）

- **状态**: 已接受
- **日期**: 2026-07-26
- **决策者**: 产品方（用户）
- **关联**: [ADR-0012](./0012-product-identity-workshop-scope.md)、[ADR-0013](./0013-creative-app-dual-source.md)、`docs/architecture/creative-app-creator-workbench.md`
- **归类**: Workshop 面（创作 + 发布）+ Host 面（草稿存储、发布门禁）+ web-module 轨

---

## 上下文

ADR-0013 把个人创意冻结为「管理面统一、运行时分轨」的**统一目录**。该决策本身有效，但落地后暴露一个产品缺口：

个人创意目前只能**管理已存在的作品**，不能**帮助用户创造作品**。

现状核对（2026-07-26，`deploy` 分支）：

| 用户任务 | 当前支持 |
|----------|----------|
| 用一句话描述想法并生成应用 | ❌ |
| 预览、对话修改、再次生成 | ❌ |
| 编辑已有内部应用 | ❌ |
| 导入本地项目 / GitHub 容器 | ✅ |
| 启动、停止、日志、删除 | ✅ |

四点根因：

1. **「创建」是假的创作入口。** `WorkshopPage.tsx:738` 的 `createTemplate()` 只收集名称与模块 ID，最终写入硬编码的 `<h1>${name}</h1><p>Generated by Natives Personal Creations.</p>`，且 `permissions` 传空数组；既不收集创意需求，也没有编辑、预览与迭代。
2. **AI 能力已存在但未接成闭环。** `write_module`（`capability.rs:1127`）已能让模型写入完整 SPA 并汇入 `module_manager::write_generated_module` 的 KI-1/KI-3 门禁，`lint_module`（`capability.rs:1211`）已能对 HTML 做不落盘预检；但两者只暴露在助理/执行引擎侧，个人创意页没有「告诉 AI 我想做什么」的入口。
3. **工程复杂度全部投在「运行作品」。** `WorkshopPage.tsx` 已达 **2481 行 / 77 个 `useState`**（`CODE_MODULE_GUIDELINES.md:133` 定义「超过 2,000 行 = 严重架构预警」），主要处理 Docker、GitHub Release、端口、health path、cwd、script、日志与启停删除。技术底座很厚，用户价值表面反而很薄。
4. **仍有接线未闭合** —— `WorkshopPage.tsx:124` 的 `void onInstall;`（`MainContent.tsx:111` 传空函数）、死复选框 `localStartAfterSave`（`:191`，无提交路径读取，见整改条目 F9）、进度 stage 名前后端不匹配（F5）。详见 `docs/architecture/creative-app-local-remediation.md`。这不是根因，但强化了「点了没感觉」的观感。

结论：不是能力缺失，而是**产品形态做反了**——名字承诺创作工具，实现是应用目录与运行管理器。

---

## 决策

### 1. 个人创意的第一职责是「创造内部应用」

导入与运行管理降为第二职责。页面主心智从「管理作品」翻转为「创造作品」。

### 2. P0 主流程（冻结）

```
描述想法 → AI 生成摘要 → 生成草稿并沙箱预览 → 对话修改 → 用户确认发布 → 继续迭代
```

1. **描述想法** — 用户输入一句自然语言需求；名称可选。P0 **不要求**填写模块 ID、端口、权限或技术栈。
2. **生成摘要** — 展示应用名称、核心功能、预计数据域与权限，用户点击「生成预览」。
3. **生成草稿** — 生成内部 Workshop 静态 SPA，过 Contract Linter 后在沙箱预览。草稿自动保存，**不进作品目录**。
4. **预览并对话修改** — 同页并排预览与修改输入。生成失败保留上一个可用修订，允许撤销最近一次修改。
5. **保存为个人创意** — 用户确认名称、模块 ID 与权限后，汇入既有原子写入并热上架。**成功后才进目录。**
6. **继续迭代** — 已发布应用提供「继续创作」；修改在新草稿完成，确认「应用更新」才覆盖运行版本；`moduleId` 与 domain namespace 始终不变。

**P0 成功标准**：用户不接触终端、ZIP、Docker 或代码，从一句想法开始，在同一页面得到可运行应用，并至少完成一次对话修改与一次正式发布。

### 3. AI 生成只产出内部 Workshop 静态 SPA

本地项目、GitHub 容器继续作为**导入 / 运行**入口，不进入 AI 生成主流程。此约束保住 ADR-0013 的运行时分轨与 Workshop 沙箱安全模型。

### 4. 形态：个人创意内置创作台

不跳转助理、不新建第四个产品面。页面分三区：

| 区域 | 内容 |
|------|------|
| **创作入口** | 首屏主操作为一句话输入 + 「生成应用」；次要入口「导入已有应用」 |
| **创作会话** | 左：需求 / 摘要 / 对话 / 状态；右：实时沙箱预览；顶：草稿名、保存状态、撤销；右上主操作「保存为个人创意」/「应用更新」 |
| **作品目录** | 「继续创作」（内部 Workshop 应用）与「已导入应用」（本地项目 / GitHub 容器）**分组**，不再平铺为同种卡片 |

### 5. 职责分层

| 层 | 权威职责 |
|----|----------|
| 个人创意 | 创作流程、草稿、预览、发布、作品目录 —— **为什么执行** |
| 助理模块 | 对话 UI、输入、消息流、工具活动、权限询问、运行状态、恢复提示 —— **怎样交互** |
| 执行引擎 | 会话与 Run、流式事件、工具调用、取消 / 重试、能力门禁 —— **怎样运行** |
| 供应商模块 | Provider、模型、凭证、路由与故障转移 —— **由哪个模型运行** |
| Workshop 内核 | 草稿校验、沙箱预览、正式写入、热上架 —— **怎样安全落地** |

个人创意**不自建第二套 AI 前端，不直接调用模型，不保存第二份 Provider 配置**。

### 6. 前端复用：只开一个接缝，不做透传层

助理的展示层组件已是**纯受控**（`MessageInput.tsx` 27 个 props、零 context 消费；`ConversationTimeline` / `RunStatusBar` / `PermissionRequestCard` / `ModelSelectorDropdown` 同理），本身即可复用。

对「再包一层 `AssistantComposer` / `AssistantConversation` / `AssistantRunStatus` / `AssistantPermissionPrompt` / `AssistantModelPicker`」应用**删除测试**：删掉后直接用现成组件，复杂性不在任何调用者处重现 —— 判定为**浅**，**不新建**。

真正的摩擦在于：这些受控组件所需的近 30 个 props 目前全部由 `AssistantWorkbench.tsx`（2413 行）内联编排，个人创意想用就得重抄一遍会话创建、Run 订阅、事件归并、取消 / 重试、断连恢复。

因此**唯一新增接缝**是把该编排提为 hook：

```
useAssistantRun({ agentKind, draftId? })
  ├─→ 返回值直接铺给 MessageInput / ConversationTimeline / RunStatusBar（现成组件）
  └─→ 内部走 AssistantGateway → 执行引擎 → 供应商路由
```

这是**深**接缝：接口小、背后是整个 Run 生命周期；局部性正确——断连、重试、事件乱序的 bug 只有一处。`AssistantWorkbench` 必须同步改用该 hook：**两个适配器才让接缝成立，一个适配器是假接缝。**

规则：个人创意只能**导入**助理组件、通过 props 与插槽改变布局与皮肤；**禁止 fork 一份自行演化**。预览器与作品目录仍属个人创意（非助理通用 UI）。

### 7. 草稿身份与存储

| 项 | 决策 |
|----|------|
| 内容 | `~/.natives/drafts/<draftId>/rev-<n>.html` |
| 元数据 | SQLite `creative_drafts` + `creative_draft_revisions`（schema **v9→v10**） |
| 身份 | `draftId` 为临时身份；记录 `conversationId`、来源（全新 / 从 `moduleId` 继续创作）、当前修订号 |
| 边界 | 不写 `modules` 表、不进侧边栏、不产生 `contract_id`；预览数据落 `draft.<draftId>` 命名空间，发布时默认丢弃 |

`draftId ↔ conversationId` 双向关联；创作会话使用正常的助理 agent 会话，模型选择、凭证失效、路由降级与重试全部服从助理与供应商模块现有规则。

### 8. 受限工具集：模型够不到正式模块目录

创作会话的能力目录**排除 `write_module`**，替换为三个草稿工具：

| 工具 | 语义 |
|------|------|
| `write_draft_module(draftId, htmlContent, name?)` | 写入前跑与发布**同一个** `contract_linter::lint_html`。lint 失败则**修订不落盘**，错误原文返回给模型自行修正，上一可用修订保持不动；成功则追加修订并刷新预览 |
| `read_draft_module(draftId)` | 读当前修订，供模型修改前对齐现状 |
| `rollback_draft_revision(draftId)` | 回退上一修订，对应用户「撤销最近一次修改」 |

**校验工具不新建**：`lint_module`（`capability.rs:1211`）已存在，入参恰为 `{ htmlContent }`、直接调 `lint_html`、不写盘、权限默认 `Allow`，与创作会话「写前自检」需求完全吻合，直接纳入创作会话能力目录即可。

三个工具的写入范围由内核钉死在 `drafts/<draftId>/` 内，因此权限档位可放宽为免逐次询问 —— **沙箱本身就是许可边界**。

### 9. 发布是 Host 命令，不是模型工具

```
用户点击「保存为个人创意」
  → publish_creative_draft(draftId, moduleId, name, permissions)      ← 新增，Host 侧
      → 读草稿当前修订
      → module_manager::write_generated_module()                      ← 唯一门禁，零复制
            KI-3 Contract Linter → KI-1 contract_id → 原子写 → 旧内容快照 → 热同步
      → 成功后草稿归档，draft 命名空间数据丢弃
```

点击即授权，不再叠加 Ask 弹窗；**模型无法调用它**。「继续创作」反向走：以已发布模块 `index.html` 为种子开新草稿，「应用更新」时再次汇入同一门禁，`moduleId` 与 namespace 不变，既有旧内容快照天然支持回滚（US-6）。

---

## 不变量

1. **单一门禁** — 正式写入只有 `write_generated_module` 一条路；草稿层零复制其逻辑。
2. **同一把尺** — 草稿与发布用同一个 Contract Linter，不存在「预览能跑、发布被拒」。
3. **模型够不到正式目录** — 创作会话工具集与 `write_module` 互斥。
4. **草稿无正式身份** — 不进 `modules` 表、不进侧边栏、不产生 `contract_id`。
5. **一份 AI 前端** — 个人创意只导入助理组件，禁止 fork。
6. **一份 Provider 配置** — 模型与凭证由供应商模块唯一权威。

---

## 明确不做（P0 非目标）

1. AI 生成本地项目或 GitHub 容器应用（仅内部 Workshop SPA）。
2. 公开分享、多人协作、联网上架（延续 ADR-0012 的 P2 后置）。
3. 完整 IDE / 代码编辑器 / 文件树。
4. 长期版本树、分支、diff 合并（P0 只有线性修订 + 撤销）。
5. 草稿跨设备同步。
6. 为个人创意新建独立 Creator Studio 产品面。
7. 在助理模块新建浅透传组件层。

## 后果

### 正面

- 个人创意从「作品目录」翻转为「创作工具」，P0 闭环可独立验收。
- 复用既有 `write_generated_module` 门禁，安全不变量零新增风险面。
- `useAssistantRun` 同时让 `AssistantWorkbench` 瘦身，Run 生命周期 bug 收敛到一处。

### 负面 / 成本

- 需新增草稿存储、三个受限工具与一条发布命令。
- 从 `AssistantWorkbench.tsx`（2413 行）剥离执行编排是**高冲突**操作。
- 草稿目录会占用磁盘，需要归档与清理策略。

### 中性

- ADR-0013 的双来源目录与运行时分轨完整保留，仅在 UI 上降为第二职责。
