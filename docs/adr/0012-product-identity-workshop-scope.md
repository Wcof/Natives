# ADR-0012: 产品身份、三面边界与创意工坊范围冻结

- **状态**: 已被 [ADR-0020](./0020-ai-native-personal-workspace-rearchitecture.md) 取代（保留历史背景；Workshop 安全防线在旧代码删除前仍有效）
- **日期**: 2026-07-19
- **决策者**: 产品方（用户）
- **关联**: Q1–Q25、ADR-0007、`module-workshop-kernel-runtime.md`（V3.2）
- **来源**: 创意工坊思路审计后的 D1–D7 拍板

---

## 上下文

Natives 文档中叠加了 Hub / App Store / 创意工坊 / 轻量 OS / AI 生成运行时等多套叙事，导致：

1. 安全约束（本地静态 SPA、Unique Origin、禁 CDN）与「零代码内嵌官方 Web」冲突；
2. 「仅 `type: web`」与「MCP/可组合单元」哲学冲突；
3. 基座持续变厚，与「薄 Steam 客户端」比喻冲突；
4. 商店/联网分发与本地个人工坊未分阶段。

需要冻结产品身份与边界，避免架构与优先级继续漂移。

---

## 决策

### 1. 产品身份（D5 + D7）

**Natives = 本机个人全能 AI 工作台。**

- 创意工坊是工作台中的 **一个域**，不是产品的唯一中心。
- 用户可在工作台上研发/生成自己的能力；满意后可「上架」到创意工坊供他人发现使用。
- **短期不做联网分发与公开上架**；先跑通 **本地个人创意工坊**，再做 Steam 式商店分享（明确后置）。

### 2. 北极星与阶段（D1 + D7）

| 阶段 | 目标 | 不做 |
|------|------|------|
| **P0 当前** | 个人全能工作台可用；本地工坊：生成/安装/热上架/沙箱运行/domain 数据长青 | 联网商店、公开评分、订阅计费 |
| **P1 本地工坊跑通后** | 打包/导出模块包；本地导入；版本与契约稳定 | 云端账号体系（除非另开 ADR） |
| **P2 以后** | Steam 式商店：个人外置能力分享给他人发现使用 | — |

「Steam 商店」是 **分发层远期目标**，不是当前架构驱动项。

### 3. 用户优先级（D2）

| 优先级 | 角色 | 含义 |
|--------|------|------|
| **主** | 意图用户（A） | 靠对话/AI 出工具，少写代码 |
| **副** | 模块开发者（B） | 手写或 AI 辅助写静态模块，依赖 Bridge/模板 |
| **并存** | 效率用户（C） | 终端 + Agent + 文件等日常工作台能力 |

成功标准以 **工作台主路径 + 本地从意图到可用模块的时延** 为主，不以安装量/商店 GMV 为主。

### 4. 能力双轨（D3）

| 轨道 | 形态 | 安装/权限/生命周期 | UI 归属 |
|------|------|-------------------|---------|
| **web-module** | 本地静态 SPA（HTML/JS/CSS + manifest） | Unique Origin iframe + Bridge + 契约/WAL | 创意工坊 / 模块管理 |
| **capability** | MCP / CLI / Agent 等 | 进程、凭证、权限中心、引擎会话 | AI 工作台 / 能力中心 |

禁止用单一 `modules` manifest 硬揉两种物理模型。数据模型与权限面必须分开演进。

### 5. 产品三面（D4）

```
A. Hub 面      — 凭证 / 环境 / 终端 / Agent 接入（官方工具）
B. Workshop 面 — 本地 web-module：AI 生成或手写 + 契约 + domain 长青数据
C. Embed 面    — 远程或官方 Web 嵌入（弱 Bridge 或零 Bridge；不进 Workshop 沙箱模型）
```

- **Workshop 约束继续有效**：仅本地、静态、sandbox 无 `allow-same-origin`、Vendored CSP、内核身份/契约/WAL（V3.2 KI-1…5）。
- **Embed 不得复用 Workshop 的 Unique Origin 租户假设** 来承载登录态远程站点；独立策略、独立入口（可称书签/外链应用）。
- **Hub 与 Workshop 共享内核能力，接口不同。**

### 6. 热上架（D6）

生成/安装成功路径必须 **事件驱动** 刷新侧边栏与模块列表（`write_generated` / install 出口广播 → UI 订阅）。

- 手动「扫描/刷新」仅作兜底。
- 不在 MVP 做全目录 `fs.watch` 作为主路径。

### 7. 架构定性（审计结论冻结）

| 命题 | 冻结结论 |
|------|----------|
| 前后端分离 | **否（工坊全链路）**。正确模型是 **宿主内核（权威）/ 壳 UI（投影）/ 沙箱租户（web-module）** |
| 技术相互独立 | **否**。身份、契约、安全语义焊在内核；容器（Tauri 等）可换，运行时契约不可当「独立前后端」演进 |
| 薄 Steam 客户端 | **否**。产品已定为全能工作台；工坊是其中一域 |

---

## 明确不做（当前阶段）

1. 联网创意工坊上架、发现、订阅、评分。
2. 把远程官方 Web 塞进 Workshop 沙箱当一等「模块」。
3. 用单一 manifest 同时描述 SPA 与 MCP/Agent。
4. 以商店冷启动指标驱动 P0 排期。
5. 为「前后端独立部署」而拆散契约/WAL/身份内核。

---

## 后果

### 正面

- 产品话术与工程优先级对齐：先工作台 + 本地工坊，后分发。
- 安全模型可证明：Workshop 与 Embed 分面。
- 双轨避免能力系统与 UI 模块互相污染。
- 热上架体验与 V3.2 生成路径一致。

### 负面 / 成本

- 需维护两套生命周期（web-module vs capability）与三套入口心智（Hub/Workshop/Embed）。
- 「Steam」对外比喻若使用，必须附带「分发后置」预期管理。
- 既有 `/store` 等命名可能夸大分发能力，后续 IA 宜降级为「本地模块」语义。

### 中性

- ADR-0007「插件层不造领域轮子 / 基座自建」仍然有效；领域轮子优先走 capability 或 web-module，而不是无限焊进内核——**新能力默认不进内核**，但本 ADR 承认既有工作台厚度，不强制回退薄容器。
