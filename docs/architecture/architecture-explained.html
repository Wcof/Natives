01

现在的大结构，基本合理

你安装的是一个 Natives。背后有三类程序，各管一类事。

管文件

文件浏览、搜索、修改，以及产品登记。

代码名称：Files Host

管 AI

模型连接、凭据、代理、用量和费用。

代码名称：Model Host

运行内置应用

打开投资或用量应用时，启动对应实例。

代码名称：App Runtime

这一层保留。投资内部的记账、估值、通知，可以各自有模块，但不必各自启动一个新程序。

02

问题：分了文件，还没有完全分清职责

举一个源码中已经看到的例子：后台通知任务，借用了网页接口来发送通知。

当前：后台工作绕到网页接口

后台通知任务
↓
网页接口处理函数
↓
发送通知

后台任务也要理解网页请求格式。网页接口一改，后台可能也要跟着改。

建议：两种入口，共用通知模块

网页接口 ／ 后台任务
↓
通知模块的公开操作
↓
发送通知

调用方只说“发送这条已确认的通知”，不用知道里面怎么发。

前端也有类似问题：持仓编辑直接读取首页内部状态。建议改成公开查询或事件，让首页自己管理状态。

03

我会怎样调整投资模块

同一个投资应用里，明确下面五类工作。优先整理现有代码，不另造一套系统。

  • 记账管交易、持仓、成本和现金。钱与数量以这里为准。
  • 算价值统一计算市值和收益。首页、持仓、卡片共用结果。
  • 取数据取行情、净值和资讯。取不到就说明缺失，不编数字。
  • 做分析使用确认的数据做目标、机会和报告，不另算一套账。
  • 发通知管发送确认、渠道、去重和重试，不接管记账。

“内部 API”就是模块的办事入口。例如“更正这笔交易”“获取当前估值”。同一程序里直接调用函数即可，不用都变成网络接口。

04

用“记一笔买入”理解调整后的流程

这是建议的职责分工示意，不是实际交易数据。

  1. 页面收集你的输入。
    把买入数量、价格等交给业务入口。
  2. 记账模块统一保存。
    交易、持仓、现金一起成功，或一起撤销，不能只写一半。
  3. 估值模块计算结果。
    有可信价格就计算；缺价格就明确告诉你。
  4. 首页、持仓、卡片显示同一口径。
    各自负责展示，不各自重算一套金额。

投资仍使用一个权威数据库。拆分职责，不拆散必须一起成功的记账操作。

代码要修：固定创建时间、吞掉读取错误、反向调用、直接访问内部对象。

规范要补：接口文档与代码对齐，明确公共状态、动作注册和检查规则。

大结构保留：一个产品、现有三类程序、应用按需运行。

“做得好”的判断标准是什么？

改通知渠道，不必改账本；改页面布局，不必改收益算法；通知失败，仍能正常记账；升级失败，用户数据仍然保留。

这些结果需要通过接口、异常路径、关闭回收和升级测试验证。把文件拆小，不能代替验证。
