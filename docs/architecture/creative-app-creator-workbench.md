### 为什么不新建助理包装组件

## 3. 数据契约

### 3.1 SQLite 迁移 v9 → v10

```sql
CREATE TABLE IF NOT EXISTS creative_drafts (
    draft_id          TEXT PRIMARY KEY,
    name              TEXT NOT NULL,
    intent            TEXT NOT NULL,           -- 用户原始一句话需求
    conversation_id   TEXT,                    -- ↔ 助理会话，可空（会话未建时）
    origin_module_id  TEXT,                    -- NULL = 全新；非空 = 继续创作
    current_revision  INTEGER NOT NULL DEFAULT 0,
    state             TEXT NOT NULL            -- drafting | generating | ready | publishing | published | archived
                      CHECK(state IN ('drafting','generating','ready','publishing','published','archived')),
    created_at        TEXT NOT NULL,
    updated_at        TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS creative_draft_revisions (
    draft_id     TEXT NOT NULL REFERENCES creative_drafts(draft_id) ON DELETE CASCADE,
    revision     INTEGER NOT NULL,
    content_hash TEXT NOT NULL,                -- SHA256(html)，与 KI-1 同算法
    created_at   TEXT NOT NULL,
    PRIMARY KEY (draft_id, revision)
);

CREATE INDEX IF NOT EXISTS idx_creative_drafts_state ON creative_drafts(state);
CREATE INDEX IF NOT EXISTS idx_creative_drafts_conversation ON creative_drafts(conversation_id);
```

迁移写在 `db.rs::apply_migrations` 的 `current_version < 10` 分支，末尾 `INSERT OR REPLACE ... '_schema_version', '10'`，并按 v9 的既有模式附一段版本外 repair path（`CREATE TABLE IF NOT EXISTS`），使携带超前版本标记的库也能补建表。仅新建表，**不 ALTER 既有表、不 DROP**。

> 早期草案里 `creative_draft_revisions` 有一列 `lint_passed INTEGER NOT NULL DEFAULT 1`。实现时删除：lint 失败的修订根本不落盘，该列恒为 1，删掉不损失任何信息，留着反而暗示存在 `lint_passed = 0` 的行。

### 3.2 文件布局

```
~/.natives/drafts/<draftId>/
├── rev-1.html
├── rev-2.html
└── rev-N.html      # current_revision 指向的即当前预览内容
```

- SQLite 是元数据唯一权威，**不写 `meta.json`**（沿用 ADR-0013 第 7 条）。
- 单个 HTML ≤ 5 MiB；单草稿修订数 ≤ 50（超出时丢弃最旧修订，但**始终保留 rev-1**）。
- 发布成功 → `state = archived`，目录保留 7 天后清理；启动时扫描过期草稿。

### 3.3 状态机

```
drafting ──generate──▶ generating ──lint ok──▶ ready
                            │                   │
                       lint fail                │ 用户点击保存
                            │                   ▼
                            └──────▶ ready  publishing ──ok──▶ published ──▶ archived
                          （回落上一可用修订）    │
                                              fail
                                                └──▶ ready（保留草稿，错误可见）
```

`lint fail` 不产生新修订、不改 `current_revision`；错误原文回传模型自行修正。

## 4. 受限工具集

工具落在**生产路径** `crates/capability-gateway/src/tools/`，注册复用既有 `register_tools_for_surface(gateway, allowlist)`（`src-agent-daemon/src/production.rs:1415`）—— 该函数已按 allowlist 精确注册工具，创作会话的受限工具集**直接用它，不新建门禁机制**。

创作会话 allowlist = 四个草稿工具，**不含** `write_file` / `apply_patch` 等通用写工具，模型因此无法触碰 `drafts/` 之外的任何路径。

> **修正记录（2026-07-26 审计）**：早期设计曾计划复用 `src-tauri` 侧的 `lint_module`（`capability.rs:1211`）并通过 `executor_catalog.rs` 控制工具可见性——**两者都不成立**：
> - `lint_module` 所属注册表 `create_default_capabilities` 的唯一调用点在 `capability.rs:1747`（`mod tests` 内），未接入生产，且位于另一个进程。
> - `executor_catalog.rs` 自述只提供 UI 设置默认值、服务于 "retired executor run path"，不控制工具可见性。
>
> 因此生产侧需要自己的 `lint_draft_module`，实现同为 `lint_html` 的薄封装。

### `write_draft_module`

```jsonc
{
  "draftId": "string",       // 必填，必须属于当前会话
  "htmlContent": "string",   // 必填
  "name": "string"           // 可选，同步更新草稿名
}
```

执行序：

1. 校验 `draftId` 归属当前 `conversationId` —— 不匹配直接拒绝（防跨草稿写入）。
2. 跑共享 crate 的 `contract_linter::lint_html(htmlContent)`（见 第 4.1 节）。**失败 → 立即返回错误原文，不触碰磁盘、不改 DB。**
3. 通过 → 原子写 `rev-<current+1>.html`（temp → fsync → rename，复用 `module_manager::atomic_write`）。
4. `INSERT creative_draft_revisions` + `UPDATE creative_drafts SET current_revision, updated_at`。
5. 广播 `db-state-changed` channel = `creative-draft`，前端刷新预览。

返回：`{ revision, contentHash, previewUrl }`。

### `read_draft_module`

```jsonc
{ "draftId": "string" }
```

返回当前修订 HTML 与 `revision`。同样校验会话归属。

### `rollback_draft_revision`

```jsonc
{ "draftId": "string" }
```

`current_revision -= 1`（下限 1，已在 1 则返回明确错误）。**不删除文件**，仅移动指针 —— 撤销可再撤销回来。

### `lint_draft_module`

```jsonc
{ "htmlContent": "string" }
```

不落盘预检，供模型写前自检。返回 `{ passed, errors }`。

### 权限档位

四者写入范围钉死在 `~/.natives/drafts/<draftId>/` 内（路径规范化后前缀校验，拒绝 `..` 与符号链接逃逸），故 `path_scope` 收窄到草稿根、`permission_class` 设为**免逐次询问**；沙箱本身即许可边界。

## 4.1 跨进程约束与 `contract-linter` 共享 crate

Agent Daemon 与 Tauri Host 是**两个进程**：

| 组件 | 进程 | 可达性 |
|------|------|--------|
| `contract_linter` | Tauri crate 内 | daemon **不可达** |
| `write_generated_module` | Tauri crate 内 | daemon **不可达** |
| `natives_db_broker` | daemon | **只读**（自述 "Opens DB read-only"），仅解密凭证 |
| `capability-gateway` 工具 | daemon | 有文件系统访问 |

不变量 2「草稿与发布用同一把尺」要求两侧跑**同一份** lint 规则。在 daemon 侧复写一份规则会立刻违反该不变量，且必然随时间漂移。

**决策：把 `contract_linter` 提取为共享 crate `crates/contract-linter`**，Tauri 与 daemon 同时依赖。

可行性：`contract_linter.rs` 仅 179 行、只依赖 `regex` + `serde_json`，无 Tauri / DB / 文件系统耦合，提取无循环依赖风险。提取后 `module_manager.rs:607` 与 `:622` 改为引用新 crate，行为不变，既有 8 个单测原样迁移。

职责分工：

| 职责 | 进程 |
|------|------|
| 草稿文件读写、修订指针移动、lint 预检 | Daemon（工具层） |
| 草稿元数据 SQLite 写入、状态机 | Host |
| 发布 `publish_creative_draft` → `write_generated_module` | Host（本就是 Host 命令，不受跨进程影响） |
| 沙箱预览 HTTP 服务 `/drafts/` | Host（`http_server.rs`） |

> 草稿工具只写文件、不写 DB；元数据由 Host 在收到工具完成事件后更新。这样 daemon 不需要任何 DB 写权限，`natives_db_broker` 的只读约束保持不变。

## 5. 发布路径

### Host 命令（非模型工具）

```rust
// src-tauri/src/commands/creative_draft.rs
#[tauri::command]
pub fn publish_creative_draft(
    draft_id: &str,
    module_id: &str,
    name: &str,
    permissions: Vec<String>,
) -> Result<PublishOutcome>
```

1. 读 `creative_drafts` + 当前修订 HTML。
2. `state = publishing`。
3. 调用**既有** `module_manager::write_generated_module(conn, modules_dir, module_id, name, html, &permissions)` —— KI-3 lint、KI-1 `contract_id`、原子写、`old_content` 快照、`sync_modules_to_db` 热上架全部沿用，**零复制**。
4. 成功 → `state = published` → `archived`；丢弃 `draft.<draftId>` 命名空间数据。
5. 失败 → `state = ready`，错误原文回显，草稿完整保留。

前端通过 `src/lib/tauri-adapter.ts` 暴露（参照既有 `write_generated_module` 封装，`tauri-adapter.ts:1095`）。

### 「继续创作」反向路径

```
已发布模块 index.html
  → 新草稿（origin_module_id = moduleId, rev-1 = 现有内容）
  → 对话修改（同一套受限工具）
  → 「应用更新」→ publish_creative_draft(draftId, 同一 moduleId, …)
      → write_generated_module 返回 old_content 快照 → 支持一键回滚（US-6）
```

`moduleId` 与 domain namespace 始终不变，模块数据不丢。

## 6. 预览沙箱

复用 `src/lib/iframe-sandbox.ts` 与既有 Unique Origin 机制，**不新建第二套沙箱**：

| 项 | 草稿预览 | 正式模块 |
|----|----------|----------|
| Origin | 独立 Unique Origin | 独立 Unique Origin |
| sandbox | 无 `allow-same-origin` | 无 `allow-same-origin` |
| CSP | 同正式模块 | — |
| Session Token | 草稿专属，发布时作废 | 正式 token |
| 数据命名空间 | `draft.<draftId>` | `<moduleId>` |
| HTTP 路径 | `/drafts/<draftId>/<file>` | `/modules/<moduleId>/<file>` |

`http_server.rs` 现有路由为 `/modules/{moduleId}/{path}`（`:215`）。草稿新增**平级前缀** `/drafts/{draftId}/{path}`，指向 `~/.natives/drafts/`。两个前缀天然不冲突，无需依赖 moduleId 命名规则。

> **修正记录**：Contract Linter **不校验 moduleId 格式** —— `contract_linter.rs` 只做三项 HTML 检查（远程脚本、内联事件处理器警告、`eval`/`new Function`）与两项 manifest 检查（`schema_version` ∈ {1.0, 1.1}、permissions 白名单）。任何依赖「linter 会挡住某种 moduleId」的设计都是错的；moduleId 唯一性由 `modules` 表主键与发布前的重名检查保证。

`sanitize_path`（`http_server.rs:183`）已实现空字节拒绝、`..` 拒绝、query 剥离与 canonicalize 后的包含性校验（防符号链接逃逸）。草稿路由**复用同一函数**，仅替换 root 目录参数 —— 不复制一份穿越防护逻辑。

发布时默认丢弃 `draft.<draftId>` 数据，避免测试数据污染正式 namespace。

### 权限白名单（发布确认界面的唯一取值来源）

`contract_linter.rs::ALLOWED_PERMISSIONS` 是权威列表，发布界面**不得**出现列表外选项：

`db:read`、`db:write`、`env:read`、`notification`、`ipc:send`、`lifecycle`、`settings`

模型在生成摘要阶段声明的「预计权限」必须映射到该白名单；无法映射的一律丢弃并在摘要中说明，避免用户在发布时才撞上 lint 拒绝。

## 9. 验收

### P0 主流程（人工）

1. 输入「做一个番茄钟」→ 生成摘要 → 生成预览 → 预览可交互。
2. 说「加一个休息提醒」→ 预览更新，内容保留原有功能。
3. 点撤销 → 回到上一版本。
4. 点「保存为个人创意」→ 确认 ID 与权限 → 出现在「继续创作」分组 → 侧边栏可打开。
5. 点「继续创作」→ 改一处 → 「应用更新」→ 运行版本更新，`moduleId` 不变，模块数据未丢。
6. 全流程未接触终端、ZIP、Docker、代码编辑器。

### 自动化

- `creative-draft.test.ts` — 状态机迁移、动作可用性、修订上下限。
- 草稿工具路径逃逸测试 —— `..`、绝对路径、符号链接、跨 `draftId` 写入均须拒绝。
- `write_draft_module` lint 失败时**不产生修订、不改指针**。
- `publish_creative_draft` 失败时草稿完整保留、`state` 回落 `ready`。
- 创作会话能力目录**不含** `write_module`。
- v9→v10 迁移幂等；旧库升级后既有数据完好。
- `npm run perf:check` 通过（`docs/standards/technical/04-performance.md`）。

### 无假数据自检

- 草稿状态、修订号、lint 错误、发布结果全部来自真实数据源。
- 生成中不显示伪造进度百分比；未知状态不显示为「就绪」。
- i18n：`src/i18n/en.ts` 与 `zh.ts` 同步。

## 10. 已知局限与缓解

### Contract Linter 不是「能不能跑」的判据

`lint_html` 只做**安全**审计：远程脚本（error）、内联事件处理器（warning）、`eval` / `new Function`（error）。它**不检查** JS 语法、运行时异常或渲染结果——一个语法错误的白屏页面完全能通过 lint。

因此 ADR-0014 第 2 条「生成失败保留上一个可用修订」**不能仅以 lint 结果判定**。P0 采用两级判据：

| 级别 | 判据 | 处置 |
|------|------|------|
| L1 硬失败 | lint 未通过 | 修订不落盘，错误原文回传模型 |
| L2 软失败 | 预览 iframe 上报 `window.onerror` / 未渲染任何内容 | 修订**已落盘**，但在预览区显式提示「本次修改可能有问题」并高亮「撤销」 |

L2 不阻止落盘——否则用户无法看到出错现场、模型也拿不到错误上下文。预览错误应回灌为下一轮对话的上下文，让模型自行修复。

> P0 不做完整的运行时健康检查；上述 L2 是最小可用信号，后续可扩展。

### 修订上限的取舍

单草稿 50 条修订上限会丢弃中间历史。P0 接受此损失（始终保留 rev-1 与当前修订），因为线性撤销只需相邻修订；完整版本树是明确的非目标。
