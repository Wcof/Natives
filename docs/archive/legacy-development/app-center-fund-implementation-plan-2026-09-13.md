# Natives 单一应用、内置模块与完整交付实施方案

> 修订：2026-09-13，依据 HEAD `9f4b21e4`、当前 macOS 安装文件及实际 PKG 展开结果，更新安装审计与实施顺序。
> **唯一产品路线：Natives 是一个完整应用，基金等功能是内置模块，全部随 Natives 一起安装、更新和修复。没有模块独立下载、安装、更新、卸载或 Release。**
> 本版替换本文件此前“独立应用包”“统一套件加二次下载”“条件备选”路线，不并行保留。
> **主入口必须可见：同一 PKG 安装 `/Applications/Natives.app`，显示正常图标和名称；首次双击自动打开 Chrome 并引导加载随包扩展，已就绪则直接进入 Natives。** 这取代前版“禁止主程序 .app、只靠安装说明找目录”的决定，内置模块仍不独立安装。
> **检查结论：路线合理，安装尚未达到普通用户顺利完成并正常使用的标准。可见主程序、离线指南和完整组件已经进入候选；首次握手接续、本地/正式隔离、更新恢复和正式签名仍有明确缺口。**
> 本轮交付是安装审计和更新方案；只读检查现有安装与产物，未重新安装、启动引导、修改 Chrome 配置或公开发布。
> P0 清理 ADR/Standards 正文中与已采纳决定冲突的旧条款，不重新讨论产品路线。模块数据、Secret、安全隔离和回收约束继续保留。

**本次重点：§1.4 用户操作与前台接续 → §2 实际审计 → §5 安装工作包 → §6/§8.4 实操验收；§10 可直接交给本地 Agent。其余章节保留完整产品与基金要求，不重新扩张本次安装范围。**

## 0. 本次决定，不再混合两种模式

| 对象 | 本次定义 |
|---|---|
| Natives | 唯一产品、唯一用户安装对象、唯一发布和更新入口 |
| Natives.app | 系统“应用程序”里可见的唯一主入口；负责双击打开 Chrome、首次引导与简短诊断 |
| 空间、文件、AI、基金 | Natives 内的功能模块 |
| 应用中心 | 内置模块的入口与偏好管理页，保留现有名称 |
| 基金代码 | 随 Natives 构建并进入完整安装包，不在首次使用时下载 |
| 基金数据 | 用户私有数据，升级/重装/修复保留 |
| Chrome 扩展 | 主应用必需的界面组件，随同一版本交付；用户完成 Chrome 要求的一次本地加载 |
| 更新 | 只提示“更新 Natives”，安装一个锁定所有组件版本的完整产品版本 |
| 修复 | 修复 Natives 安装，或有证据地恢复同一产品版本的受损文件；不重新下载某个模块 |

取消的产品能力：

- 应用中心的“可添加/应用商店”、模块安装/下载进度、模块独立升级、模块卸载。
- 运行时发现任意新 appId，在线目录驱动新业务，Fund 的独立模块发布。
- 自动下载“未随附模块”、把模块首用称为安装、两种生产模式切换开关。
- 独立应用包方案及其备选分支。今后如要重新引入，属于另一次明确产品决策，不在本轮预留平台。

基金源码可以继续按清晰领域边界维护，但用户版本、安装包和 Release 与 Natives 联动。内部使用几个受控程序属于实现细节，不形成可单独安装的产品。

## 1. 最终用户流程

~~~text
下载一份 Natives 安装包
  → 双击安装
  → “应用程序”中出现有名称和图标的 Natives
  → 双击 Natives
  → 自动打开 Chrome；首次显示扩展引导并定位随包目录
  → 用户按提示开启开发者模式、加载已解压目录
  → 扩展前台真实握手并完成当前用户的 Natives 产品配置
  → 空间、文件、AI、应用中心可使用
  → 应用中心点击“基金：打开”
  → 直接使用内置基金，首次仅做必要的数据初始化
~~~

基金初次打开不下载代码，不安装第二个程序，不要求选择基金包、不显示“安装基金”。当前用户的产品配置从已安装的完整产品中校验全部固定模块并完成注册，见 §3.3；必须在报告产品就绪之前完成，不能拖到应用中心或首次打开基金时做。

以后：

- 双击系统中的 Natives，或点击 Chrome 扩展图标进入；已有连接成功时直接进入产品，不重复安装引导。
- 有新版只出现“更新 Natives”；更新包含主程序、浏览器组件及所有内置模块。
- 模块卡片只负责打开、显示/隐藏、偏好和必要的错误说明。
- 用户隐藏模块不卸载代码；清除模块数据是另一个明确的危险操作。
- 日常不需要源码、Node/npm/Rust、Terminal、npm run dev 或手工 Native Messaging 配置。

用户此次要求明确改变主入口约束：**必须有 `/Applications/Natives.app`，不得把主应用隐藏成只有后台文件。** ADR-0029 已记录唯一主产品入口例外；基金等模块仍不创建独立 `.app`。安装说明作为辅助，不能替代可找到、可双击的 Natives。

Chrome 最终选择包含 manifest.json 的**解压目录**，不能直接选择 ZIP。本地加载和重载遵循实际浏览器步骤，不使用普通 Chrome 的 --load-extension 自动加载。[Chrome 官方加载说明](https://developer.chrome.com/docs/extensions/get-started/tutorial/hello-world)

首发平台按真实证据声明。macOS arm64 与 macOS x64 分别对应 Apple Silicon 与 Intel；未做实机验收的平台不标可用。

### 1.1 安装后可见与双击行为：本次强制补充

**安装后的可见性：**

- Finder“应用程序”内必须出现 `Natives.app`，显示名称 Natives、正式应用图标和版本信息，能够双击启动。系统应用列表/启动台（目标 macOS 提供时）及 Spotlight 搜索按正常应用登记验证，不以重建用户系统索引冒充修复。
- 使用正常 application bundle、Info.plist 和本机 GUI 入口；不设置 Hidden、LSUIElement 或 LSBackgroundOnly 来隐藏主入口。不用裸 CLI/Shell 文件充当用户双击程序，不弹 Terminal。
- Launcher 退出后，已安装的图标仍在“应用程序”中；引导关闭不等于卸载。Dock 可在引导运行时正常显示，是否固定由用户决定，不强制改 Dock 设置。
- 缺这个可见入口即视为安装不完整，即使 Host 可以连接、扩展可以打开，也不能通过安装验收。

**双击后的行为：**

| 情况 | 必须执行的动作 |
|---|---|
| 首次使用 / 尚无本次连接证明 | 自动打开 Chrome，显示 Natives 的简短引导窗口；尝试打开扩展管理页，自动在 Finder 显示随包扩展目录 |
| 扩展尚未加载或被停用 | 引导开启开发者模式、点击“加载已解压的扩展程序”、选择已定位的目录；停用时提示启用。不能仅凭超时区分未安装、停用和 profile 错误 |
| 扩展已可用 | 本次前台握手确认扩展 ID、实际版本、产品状态后，打开/聚焦 Natives 产品页；不再弹安装教学 |
| 扩展刚加载完成 | 扩展单次安装事件/前台页面接续引导，完成产品配置后进入空间；不能要求用户回源码目录启动服务 |
| Chrome 尚未安装 | 保留可见引导窗口，显示“需要 Chrome”及官方获取入口、重新检测；不静默安装浏览器或换成测试浏览器 |
| profile 错误、版本冲突或本机文件异常 | 显示对应检查/重载/修复说明；未确认时显示“尚未连接”，不能显示“已安装成功/已就绪” |
| 引导期间再次双击 | 激活已有引导窗口；成功后重复打开优先聚焦同一 profile 的既有产品页，不堆积窗口和后台进程 |
| 用户关闭或取消 | 结束此次引导和有界检测；应用图标保留，再次双击可继续。成功交接后 Launcher 也退出 |

引导窗口只有必要文案和按钮：`打开扩展管理页`、`显示扩展文件夹`、`复制目录路径`、`重新检测`。目录是已安装产品里的固定真实目录，不让用户去网上另找 ZIP。用系统原生窗口承载，业务界面仍在 Chrome。

自动检测必须关联本次启动会话及经过 Core origin 校验的前台握手；复用现有握手状态通道，增加本次 challenge/过期关联，不能继续以旧文件存在或 mtime 判定成功。只在当前可见引导期间有界等待，沿用现有最长十分钟限制，超时提供重试；无新常驻检测服务、远程调试端口或 Service Worker 长连接。

### 1.2 扩展自动安装的明确边界

按当前“免费、本地随包分发、普通 macOS Chrome”路线，自动完成安装文件准备、打开 Chrome、展示引导和定位目录；**开发者模式与加载目录由用户按浏览器要求操作**。Chrome 官方说明 Windows/macOS 的外部安装依赖商店来源且仍有启用确认，本地 CRX 不属于这条自动安装通路。[Chrome 外部安装规则](https://developer.chrome.com/docs/extensions/how-to/distribute/install-extensions)

本轮不实现企业策略注入、Chrome profile 篡改、无障碍自动点击、静默 CRX 安装或商店后备链。若将来改走商店/企业受管分发，另行明确分发决定；当前验收按上述本地加载路径完整完成。`chrome://extensions` 不能假设从普通网页链接打开，Launcher 应通过系统浏览器打开能力尝试，并在失败时提供地址复制及 Chrome 菜单操作。[Chrome 本地加载步骤](https://developer.chrome.com/docs/extensions/get-started/tutorial/hello-world)

### 1.3 随包离线 HTML 安装引导页：保留并完善

当前已经有随包 HTML，应完善现有模板。它提供扩展尚未安装时也能阅读的说明；原生窗口保留系统操作与真实状态。无需新建引导框架或在线帮助服务。

**交付位置和打开方式：**

- 源文件复用 `installers/macos/resources/onboarding-template.html`（中英文来自同一份内容），最终进入 `Natives.app/Contents/Resources/onboarding/`；同一文件的摘要纳入产品组合清单和签名。
- PKG 安装完成页（Distribution `conclusion`）显示离线引导的短摘要：告诉用户去“应用程序”打开 Natives、首次会打开 Chrome、需要完成三步扩展加载。不能在结尾页复制第二套完整步骤。
- 用户双击 `/Applications/Natives.app` 时，Launcher 先打开 Chrome 中的 `file:` 离线指南，并同时显示原生状态窗口。指南不依赖扩展、Native Bridge、本地 HTTP 服务、业务数据或网络；Chrome 尚未安装时改由原生窗口显示同一内容的降级摘要。
- 已连接扩展后不再重复打开指南；用户从 Natives 的“帮助/重新查看安装说明”进入时仍可重新查看同一版本指南。更新产品时指南和主程序同版本切换，不从网上加载远程 HTML。

**页面内容必须包含：**

1. 当前 Natives 版本与“首次使用，请完成以下步骤”的说明。静态页面不显示“未连接/已连接/安装完成”等实时状态；用户从帮助重开指南时，内容仍成立。
2. 三步图文说明：打开 `chrome://extensions`、打开开发者模式、点击“加载已解压的扩展程序”并选择随包目录。明确选择目录而不是 ZIP，并显示实际目录的复制文本。
3. “之后怎么打开”：以后从“应用程序”双击 Natives；扩展已经加载时会直接进入；基金在应用中心中直接打开，不显示安装基金。
4. “常见问题”：没有 Chrome、页面打不开、扩展被停用、重复加载、目录权限错误、Chrome profile 不一致、重新安装/升级后如何重载，以及如何返回 Natives。
5. 高级帮助折叠展示真实扩展目录、版本与诊断信息；日常步骤不要求核对长扩展 ID、引导会话编号、Host 路径或仓库文件。数据说明只保留用户需要知道的本地保存与卸载保留规则。
6. 中英文、离线可用、无外部字体/CDN、键盘可访问、浅色/深色跟随系统，窗口较窄时步骤仍可读。页面只使用本地 CSS 和语言切换等展示脚本；不嵌入业务 UI，不自动请求网络资源。用户主动打开的固定 Chrome 官方下载/帮助链接可以保留。

**状态职责必须分开：**

| 模块 | 负责 | 不负责 |
|---|---|---|
| 离线 HTML 引导页 | 解释步骤、显示版本/目录文本、语言切换、帮助和常见问题 | 检测 Native、修改 profile、打开内部 API、声称安装成功 |
| Natives.app 原生 Launcher | 打开 Chrome、尝试打开扩展管理页、在 Finder 定位目录、展示实时检测/错误、聚焦已有窗口 | 渲染空间/基金业务、持有 Secret、实现第二套安装事务 |
| 扩展首次配置页 | 真实 Native 握手、产品清单校验、当前用户配置和就绪状态 | 在握手前读取基金数据、从网络下载模块、把旧 handshake 文件当成功 |
| PKG conclusion | 安装结束的静态下一步摘要 | 运行脚本、检测 Chrome、动态显示已连接 |

Launcher 按 bundle 资源位置打开静态 HTML，不给说明页生成无用途的 session id，也不在说明页展示随机编号。真正的本次启动 challenge 只用于 Launcher 与经过 Native origin 核验的扩展前台确认连接，见 §1.4；说明页不参与鉴权。

**实施和验收要求：**

- 在构建阶段从一份内容源生成 `index.html`、PKG conclusion 摘要和两套 locale；CI 检查三者的版本、步骤标题和目录文本一致，禁止手工维护两份说明。
- 包扫描必须确认 HTML、CSS、图标都在 `Natives.app` 内，仅允许本地资源、固定 `chrome://extensions` 文本与用户主动打开的固定官方帮助链接，不出现远端脚本、`eval`、Native Port、localhost、业务参数或开发机绝对路径。
- 在没有扩展、没有网络、首次安装、用户关闭引导、Chrome 不存在、错误 profile、扩展已加载、重复双击、产品升级后重载九种路径验证。页面打开成功不等于扩展安装成功；必须以真实握手结果判定后续状态。
- HTML 只能由受信本地文件路径打开；禁止把用户输入的路径拼进 URL 或允许页面跳转任意 `file:`/HTTP 地址。复制目录只复制固定安装目录的文本；保留可选中文本作为失败回退。只在用户点击“复制目录路径”时改剪贴板，不因打开应用自动覆盖用户剪贴板。


### 1.4 让用户少操作，但每一步确实接通

本轮保留现有 DMG → PKG 分发方式：下载入口只推荐一个对应芯片的安装文件，DMG 里只突出“安装 Natives.pkg”，不要摆放第二个可拖拽安装的 Natives.app。高级下载可提供同一个 PKG；用户不用在 ZIP、扩展包、基金包和源码之间选择。

| 阶段 | 用户操作 | 系统完成 / 明确结束条件 |
|---|---|---|
| 系统安装 | 打开安装文件，按系统提示授权 | 一次安装主入口、主 Hosts、扩展及全部内置模块；结束页告诉用户“到应用程序打开 Natives” |
| 首次双击 | 双击 Natives | 尽快显示原生“正在连接”状态；首次打开离线指南并定位目录。避免多窗口反复抢焦点，不自动改剪贴板 |
| 加载扩展 | 在 Chrome 开启开发者模式，点击加载已解压目录并选择固定目录 | 这是浏览器必需的人工步骤；指南按实际菜单说明，找不到目录可用选择器中的 Cmd+Shift+G 粘贴固定路径 |
| 前台接续 | 加载后自动进入配置；自动打开未发生时点击扩展图标 | 扩展单次安装事件只打开/聚焦现有扩展前台配置入口；Native Port 归前台持有，不归 Service Worker |
| 完成配置 | 只点击一次“完成 Natives 配置” | 当前用户完成全部固定模块校验、私有载荷/注册/activation；成功后直接进入空间，基金可以打开 |
| 日常使用 | 双击 Natives 或点击扩展图标 | 本次连接核验后聚焦产品；已完成配置不再显示教学，失败回到可恢复提示 |

**前台接续的具体改法：**

- 复用现有设置/产品配置界面作为首次配置入口；需要路由时只给现有扩展页面增加受控 setup 模式。不复制一个新的工作台，也不把完成配置藏在“设置 → 应用中心”三级路径。
- `background.js` 的 `onInstalled` 当前只有日志。首次安装时打开上述前台入口；扩展更新时由实际版本/配置状态决定是否提示，普通 worker 唤醒不反复开页。原有扩展 action 也路由到同一入口，完成后仍可去正常产品页。
- Launcher 先建立一次有期限的请求，再打开目标前台入口；页面经 Chrome 提供的 caller origin 校验后，通过既有 Host 通道读取/应答这次请求。应答至少绑定 mode、本次 challenge、扩展 ID/实际版本、产品清单摘要、协议与当前用户配置结果。
- 复用现有受限握手状态文件，将其变成原子写入的本次结果；过期、旧版、不同 mode、重复消费和不匹配 challenge 均不能让本次启动成功。不要把任意网页 query、页面自报 origin 或 30 天旧记录当认证。
- 首次安装事件没有 Launcher URL 参数时，前台可通过已核验的 Host 读取本用户尚有效的待完成请求；没有待完成请求也可以执行正常首次配置。HTML 不读取此请求。待完成请求/结果仅限当前模式的用户私有根、限制权限/大小/有效期，并随取消或成功失效；请求本身不授予文件、进程或业务权限。
- Native Messaging origin 只能标识扩展，不能证明 Chrome profile 名称。成功表示发起此次前台接续的实际页面可用；没有证据时只说“尚未连接”，提供“在已加载扩展的 Chrome 用户中点击 Natives 扩展图标”，不读取/修改 Chrome 私有 profile 配置来猜测。
- 普通文件页自动发出的 version 握手只表示该连接的信息，不能自动完成全产品配置或让另一等待会话成功。配置成功和真实连接成功均满足才交接。
- 已打开页面的聚焦由扩展在当前 profile 内按固定路由处理；Launcher 重复启动使用原生应用重开事件激活已有窗口，不增加第二个监督服务。

**等待、错误和取消：**

- 原生主线程不执行 `waitpid` 或 60 秒同步 Host 等待。使用系统异步任务/退出回调，在同一小窗口更新状态；等待期间所有按钮仍可操作。
- 自动等待累计最多 10 分钟；超时停止检测并保留“重试/关闭”。用户重试才开启新一轮，不能只改一句超时文案后继续循环。
- 取消/关闭/成功交接均终止并回收本次等待进程，不关闭 Chrome。目标：启动后 1 秒内有可见反馈，取消后 2 秒内结束本次 Launcher 等待；以指定测试机实测记录为准。
- Chrome 通过系统应用发现能力定位；支持正常的系统级或当前用户安装。缺 Chrome 时，“获取 Chrome”用系统默认浏览器打开官方页面，不能调用不存在的 Chrome 打开下载链接。
- 打开指南、扩展管理页、Finder、复制路径的错误各自返回并显示可执行下一步；`open` 命令成功只证明请求已提交，不证明目标扩展已加载。
- 扩展文件夹默认展示固定真实目录。已有 Downloads 快捷方式只能作为辅助；如保留，local/production 使用不同名称，真实文件/目录或非本产品链接存在时保持原样并回退真实目录。禁止 `ln -sfn` 替换用户条目，也不在两处分别实现链接逻辑。

## 3. 架构：保留必要分工，取消模块分发系统

### 3.1 一个产品组合

~~~text
Natives 完整安装包 / 唯一产品版本
 ├─ /Applications/Natives.app：可见薄入口与首次引导
 ├─ Chrome 界面组件
 ├─ Files 本机能力
 ├─ Model 本机能力
 └─ 基金内置代码与界面

打开某功能 → 现有受控能力按需工作
关闭页面 → 正确保存/取消并回收资源
更新产品 → 所有组件按同一组合清单切换
~~~

复用现有 Files/Model/Fund 程序和 app-host-support。无需新建聚合 Runtime、modules-host、动态模块加载器、通用 invoke 或另一层后台服务；也无需为了“一个应用”合并各领域数据库。

基金现有 UI 可继续构建期嵌入受控基金执行程序，经现有 app.html 和受限 iframe 展示。它是安装包内固定业务代码，不是应用中心下载的插件。保留 appId=fund、现有页面路由、运行锁和数据目录，避免无意义重命名。

### 3.2 唯一清单与状态权威

复用现有 suite/构建元数据，收敛为一份已签名的产品组合清单：

- 产品版本、平台/架构、Launcher bundle ID/文件摘要、固定扩展 ID、兼容协议。
- 每个必需文件的相对路径、长度、最终 hash 和签名身份。
- 内置模块列表及其固定入口、名称、构建版本、数据 schema 兼容范围。
- 组件版本可作为内部构建追踪信息；用户只看到 Natives 产品版本。

清单只描述安装包已包含的固定文件，**没有模块下载 URL、安装脚本、用户自定义入口或运行时添加模块能力**。新模块只能通过新的完整 Natives 版本增加。

权威分工：

| 事实 | 来源 |
|---|---|
| 本产品包含哪些模块/文件 | 当前已验证产品清单 |
| 模块是否可用 | 实际文件/身份/协议与必要只读检查，不由旧 installed=true 推断 |
| 显示在侧栏、是否启用入口 | 复用已有用户偏好记录 |
| 基金数据/迁移状态 | 基金数据域 |
| 当前是否使用中 | 实际 owner/运行锁，作为内部维护依据 |

旧 App Store 表按需要保留用户偏好、历史收据、迁移证据及受控运行所需的固定模块投影，不继续代表可独立安装的远端应用。投影由完整产品配置维护，不新建第二 Registry。

### 3.3 安装与运行边界

- 同一个系统安装器同时放置 `/Applications/Natives.app` 和 `/Library/Application Support/Natives/` 下的主 Host、固定扩展及全部内置模块文件；最小 Native Messaging 注册由同一清单生成。Launcher 只保留一份，主程序/模块版本属于同一组合。不写用户 DB/activation，不以 root 执行基金迁移。
- 本版统一将 Chrome 实际加载目录定为 `/Library/Application Support/Natives/ChromeExtension/`，包内即为包含 manifest.json 的完整解压目录。它随整包切换，不再同时维护用户扩展副本、文本 current 或首次联网解压链。P0 将此路径写入现有契约；root-owned 固定代码目录与用户数据目录严格区分。
- 可见薄入口复用 `launcher_setup.rs` 的打开/定位/诊断逻辑及平台原生窗口，按 §1.1 接通双击；已有打包器的 Info.plist/图标资产按需复用，禁止另建业务桌面界面或常驻进程。系统主 Host 仍由固定系统路径注册，不指向旧 Contents/Runtime 猜测路径。
- **当前用户的产品配置是产品安装的收尾步骤**：扩展首次配置页通过已有主 Host 连接，在明确的“完成 Natives 配置”操作下校验当前完整清单，为全部固定模块准备私有活动载荷、浏览器注册和 activation。复用既有锁、校验、落盘和恢复逻辑，不新增安装数据库。输入不接受模块选择、URL、任意路径、Host 名或执行参数。
- 活动模块程序和数据继续位于 `~/.natives/apps/<appId>/`；系统源中的固定模块文件是完整产品安装内容，不能直接将活动执行程序移到系统源以绕过私有根约束。产品配置从可信本地安装内容完成，**无逐模块载荷协议、无独立安装记录、无应用中心自动补装**。
- 一次产品配置以同一 `productGeneration` 绑定所有模块。全部必需模块和注册验证成功后才标记本用户产品就绪；中断则阻止业务并提示“完成 Natives 配置/修复 Natives”，从同一产品事务恢复。不能部分成功却展示整体可用。
- 模块首用只在当前用户权限下做业务数据初始化/迁移。`apps:list`、应用中心打开和普通模块 `open` 不能隐式补复制代码或写注册；未完成配置应回到产品配置入口。
- 现有 activation 投影保留，但绑定签名产品清单中的固定模块、产品 generation、受控私有路径及调用身份；管理偏好 revision 变化不触发程序重新激活。
- 主 Host/基金模块按页面 Native Port 使用；Model Host 仅在用户已明确开启现有驻留设置时驻留。无通用常驻 Runtime、SW Port/轮询、Login Item/LaunchAgent/Jobs。
- Secret 不进页面；基金库不归 Files/Model 写；iframe 的 sandbox、鉴权、loopback 限额与 EOF 回收保留。
- 开发与正式身份、目录、签名、注册和 Keychain 必须隔离，不能靠改为整包发行绕过平台信任。

### 3.4 列表与操作契约：在现有接口上改，不新建平台

复用 `apps:list`、既有记录/偏好和导航投影。列表是“当前产品固定模块定义 + 该用户偏好 + 已知就绪情况”的读取投影，不依赖 apps 表中有安装记录。

| 返回事实 | 必要字段/含义 |
|---|---|
| 产品 | 产品版本、generation、配置状态（未配置/就绪/需修复/不兼容）及明确错误码 |
| 固定模块 | app_id、来自组合清单的多语言名称/说明、受控路由标识 |
| 用户选择 | 沿用 enabled、show_in_sidebar、sidebar_order；缺省值仅用于从未作出选择的用户 |
| 可用性 | 是否可打开及原因；来自当前产品验证结果，不使用远端候选包兼容性推断 |
| 数据状态 | 只返回已知信息；未检查为 unknown。需要最新业务状态时由当前模块 owner 查询，普通列表不得启动每个模块或打开其业务库 |

字段命名按现有契约统一，以上不要求新建通用状态机/Registry。不得再用 download_url、availablePackages 或在线目录版本决定用户按钮。空旧 apps 表 + 含 fund 的有效产品清单必须产生基金卡片；产品配置未完成时卡片提示产品配置，绝不能显示“安装基金”。

| 操作 | 实施约束 |
|---|---|
| 握手、列表 | 握手失败后停止后续依赖请求；列表不触发代码下载、注册、数据迁移或自动修复 |
| 打开 | 校验固定模块和产品 generation；优先聚焦当前 profile 的同一模块页，不在其他 profile 搜寻或跨用户接管 |
| 显示/隐藏、历史入口开启 | 仅修改既有偏好和投影；不增删程序/注册，不重启或终止正在打开的模块 |
| 数据清除 | 独立实现 §4.3；禁止路由到 uninstall、remove_activation 或删除模块根目录 |
| 旧模块分发请求 | 不存在于当前协议白名单；客户端升级后只能使用产品配置、模块偏好和数据管理方法 |
| 产品配置、更新、修复 | 只在现有产品配置/设置入口执行，固定完整产品输入，复用底层事务；不是页面每次连接后的副作用 |

升级时旧用户状态由产品迁移在锁内按已有 journal 安全收尾，不能为此继续开放旧客户端提交。旧客户端遇到协议变更显示“更新 Natives/重新加载扩展”，不静默回退到旧目录或旧协议。

去掉“可添加”、推荐市场、安装/下载、单独版本/更新、模块卸载、启动/停止/重启、PID/Host 状态。产品更新统一放现有设置中的“关于/更新 Natives”，不重复出现在各卡片。

### 4.2 状态和行为

| 状态 | 用户看到 | 行为 |
|---|---|---|
| 内置功能可用 | 打开 | 直接进入；已有页面优先回到原页面 |
| 显示在侧栏关闭 | 仍可在中心打开 | 仅改变导航，不下载、不删除、不停止正在使用的页面 |
| 历史记录为停用/已移除 | 入口未开启、开启入口 | 保留旧选择；开启只改偏好，代码已经随产品交付 |
| 首次数据初始化/迁移 | 具体初始化进度 | 无代码下载、无“正在安装基金” |
| 当前用户尚未完成产品配置 | 完成 Natives 配置 | 进入产品配置流程；应用中心不自动写文件、基金按钮不变成安装 |
| 文件损坏/版本不兼容 | 功能暂不可用、查看原因 | 引导“修复 Natives”或“更新 Natives” |
| 数据损坏/迁移失败 | 数据需要处理 | 给出备份/恢复说明；不伪装成安装问题、不自动清库 |

隐藏、停用和清数据不能互相代替。默认不增加新的模块停用功能；只承接旧用户的明确停用/移除意图，用户开启后恢复正常入口。

### 4.3 数据管理

- 查看数据说明与必要占用；未知大小明确未统计，不伪造 0。
- 导出/备份沿用现有能力；清除基金数据与 Keychain 按现有规范二次确认，确认页列出实际范围。默认保留登录凭据，删除凭据必须单独勾选确认。
- 关闭/隐藏入口保留数据。修复、重装、产品升级同样保留。
- 不提供名为“卸载模块”的操作，因为模块代码仍属于整包。

**清数据的具体实现要求：**

1. `apps:clear_data` 是唯一数据删除动作；先验证固定 appId、当前产品、确认范围、幂等 requestId 和 caller，再持有既有操作/运行锁。业务仍在使用时提示保存关闭，不强制结束或边写边删。
2. 只处理该模块的数据目录及用户明确选择的 imports/cache/日志/Keychain namespace。每个目标做既有路径与链接边界校验，禁止递归删除 `apps/<appId>/` 整体。
3. 保留程序文件、签名记录、权限、Native 注册、activation、产品清单/generation、显示/启用/排序偏好；不写 removed 意图、不删固定模块身份。
4. 复用持久清理收据/journal，存放在本次清理范围外，明确区分数据重置与历史卸载收据。失败显示 cleanup_pending、具体未完成范围并允许同一确认操作重试；完成的 requestId 重放只返回原结果，不能把后来录入的新数据再清一次。
5. 清理未完成时暂不开放该模块写入；成功后数据状态为空，重新打开由模块正常初始化。其他模块的数据与凭据不动。

验证必须比较清理前后代码 hash、注册、activation 和偏好；仅断言 DB 不存在不够。导出备份到模块范围之外的用户文件，不被此次清除连带删除。

### 4.4 外观与状态同步

- 独立应用中心、设置内嵌中心和 app.html 复用产品管理面外观偏好；空间 Widget 使用空间局部规范。
- 查明当前生产主题协调器，统一 dark/light 和历史别名映射，删除重复监听，不建立另一 localStorage/chrome.storage 权威。
- 使用 extension 当前 CSS tokens、图标和弹窗；不恢复历史 src/Tauri 组件。
- 中英文、字号层级、焦点、禁用态、错误和小窗口可访问；主题切换不会重启基金。
- sidebar/偏好/失败通知只更新相关展示；bfcache 恢复所需监听与握手，撤销旧 token。
- 不在普通 UI 暴露内部进程和调试字段。

### P1：一个构建入口、一个安装布局

### P2：内置模块读取与旧数据迁移

**本次重点 D08/D09：修复现有 `app_store/product.rs`，不要另造事务平台。**

- `product_status` 区分尚未配置、正在配置、就绪、需要完成更新、需修复和不兼容；读取签名源失败返回真实原因。就绪要求当前已验证组合摘要与本用户已应用组合一致，全部固定模块的注册/activation/文件证据一致；generation>0、目录存在或有旧 apps 行均不足。相同清单快路径仍要识别文件/注册丢失，不能让同版重装失去修复能力。
- 在既有跨进程操作锁下读取并验证同一份清单字节；其摘要也从同一缓冲区计算，避免二次读取切换。验证完整固定模块集合、唯一 appId、版本/路径/链接边界、长度/hash、协议与签名；生产新候选缺必需字段不能静默当旧格式兼容。
- 复用现有 staging、journal 与恢复原语，为本次产品事务隔离 staging；先取得相关运行锁/维护条件再切换，不能锁外删另一个调用的 staging。产品版本降级在用户数据变更前拒绝。
- journal 记录产品清单摘要、目标 generation、各模块旧/新载荷及注册/activation 的恢复步骤。所有模块应用成功才提交产品就绪；任何一步失败允许恢复同一事务，所有入口在 pending 时拒绝依赖业务。不要仅依赖同一进程的 Mutex 或“再点一次”。
- activation 与 DB 偏好一致，不能写死 enabled=true；每个固定模块投影绑定同一产品 generation。保留历史 disabled/removed 选择、侧栏与 Keychain，不主动唤醒被关闭的功能。
- 在每个副作用切点注入中断，以及双前台并发配置，验证不会得到部分就绪。这个故障测试复用既有临时根和进程测试能力，不建立第二个测试框架。

- apps.js/native-app-client/App Store 查询和导航投影按 §3.4 改造；无远端发现依赖。空 apps 表也返回产品声明的基金；未知可用性不伪装可用或未安装。
- 删除页面对模块分发的调用；握手不兼容后不再 list 或写入。旧客户端方法不在 Host 白名单，不能只隐藏按钮。
- 复用安装校验、文件限制、身份函数和恢复工具，在**产品安装/更新**层使用；避免以删除旧路由为由删掉安全能力。
- `clear_data` 按 §4.3 拆离 uninstall；审计其所有调用者、历史 retained-data 入口和失败重试，防止任一路径继续移除固定程序/偏好。历史真正卸载收据只允许在受控产品迁移中收尾。
- activationGeneration 与管理 revision 分开；固定模块激活验证实际产品清单、受控程序、caller 和协议。
- 老 fund 安装记录按精确 appId/receipt/schema 迁移；保留原数据、Keychain、sidebar_order 和显示/停用选择。
- 老 removed/disabled 转成入口关闭偏好，整包重装不擅自打开；不显示已移除代码，因为新版确实包含它。
- 旧独立基金版本高于整包内兼容版本时拒绝隐式降级，先提供能承接数据的完整新版。不能以清库完成迁移。

- 切换后只激活固定产品程序；旧动态注册不能作为静默 fallback 继续运行。

交付：新用户完成一次产品配置后直接打开基金；旧用户数据和选择不丢。清数据后代码/注册/偏好仍在；应用中心读取不发起任何安装事务。

### P5：整包更新、修复与恢复

**本次补齐 D08/D09/D12 的系统侧与用户侧衔接：**

- 只有产品级“检查更新/更新 Natives”；来源为可信完整产品 Release，按已有设置和前台动作触发，无后台轮询。
- 检查新组合版本、平台、全部文件/身份与扩展兼容性。缺任何必需组件不切换。

## 7. 基金内置模块的业务验收

### 7.1 本次范围

本阶段目标为随 Natives 完整交付的基金内置模块：账户、基金、持仓、确认交易、手工/文件导入、净值和基础市值/盈亏展示，以及完整的数据与生命周期保护。

现有审计报告中的养基宝登录、跨市场行情、穿透估值、FundScore、风险分析与 AI 解释，不自动全部纳入本次模块整改。不得做成假入口。P0 用“本次交付/后续候选”矩阵记录；若用户已有其他已确认基金需求，补入矩阵并实现相应工作包，不能被本方案静默删减。

当前相邻基金仓库已有业务和 UI 源码；其完整性须在 P0 重新核验。本轮只审计应用中心，不将已有源码视为基金验收通过，也不按早期“没有实现”的描述重建工程。

### 7.2 首版资金与记账口径

- 只处理人民币场外基金的已确认交易；币种固定CNY。股票/外汇/多币种、场内买卖、自动交易不在本次范围。
- amount、fee、cost_basis、realized_pnl以元为单位，输入最多两位小数；quantity与基金NAV/price最多四位。多余有效精度不静默截断，返回校验错误。
- 内部采用有界十进制数及溢出检查；截取到指定精度统一向零截断（ROUND_DOWN），不是二进制浮点或负数floor。中间乘除不提前量化，落账的金额/费用/成本分配量化到两位，持仓份额四位。
- amount表示不含费用的已确认成交金额；BUY计入成本amount+fee，SELL净收入amount-fee。未提供amount时由quantity×price截取两位生成；提供时与该值差异超过0.01元即作为冲突进入导入预览/人工更正，不能悄悄改账。金额和份额必须正，费用非负，卖出费用不得大于成交金额。
- 卖出使用移动平均成本：扣除成本=当前成本×卖出份额/当前份额，最终截取两位；已实现收益=卖出净收入-扣除成本。全部清仓时扣完剩余全部成本，避免分钱残留；任何时间点按稳定顺序（交易日期、确认时间、内部ID）重放结果一致。
- 平均持仓成本价与展示NAV可显示四位，但已四位显示的均价不能回写成本计算。缺成本的期初记录保持cost_basis=null，相关收益显示不可计算；不得补零后产生假利润。
- 交易日期按Asia/Shanghai的YYYY-MM-DD解释；净值日期按数据源原值保存，节假日/缓存不改写成今天。卖出超过重放所得可用份额直接拒绝。
- 本节黄金用例必须作为精确断言；另覆盖分币成本、负收益、全部清仓、溢出和同日多笔顺序。

### 7.3 CSV模板与导入身份

首版只支持UTF-8 CSV（可有BOM，标准双引号转义），不承诺XLSX。文件≤5MiB、数据行≤20,000、单字段≤4KiB；界面选择模板版本1，不通过任意脚本/表达式映射列。传输复用应用业务HTTP的分块上传，每块≤256KiB，预览分页，不突破通用请求上限。

| 模板 | 必填列 | 可选列/规则 |
|---|---|---|
| 已确认交易 | account,fund_code,trade_date,type,quantity,price | amount,fee,external_id；type为BUY/SELL；fee缺省为0，amount按7.2计算 |
| 期初持仓快照 | account,fund_code,as_of,quantity | cost_amount,market_value,earnings,nav,nav_date,external_id；成本缺失时允许以市值减收益推算但必须标记，结果为负需人工更正；无法推算则保留未知成本 |

account映射到本地唯一账户，缺失账户先在预览中确认创建；fund_code为六位数字字符串，保留前导零。快照仅用于尚无该账户/基金记账历史的期初建账；已有流水时返回冲突，不覆写positions或编造反向交易。

持久化import_runs：sourceId、templateVersion、原文件SHA-256、导入参数/账户映射摘要、确认requestId、状态和结果；行记录保留原行序号、规范化字段摘要和结果。精确重复（同source/template/rawHash/参数）返回原结果，不再次入账；同requestId不同payload摘要返回conflict。

有可信external_id时以(sourceId,accountId,external_id)去重；相同ID内容变化进入冲突预览，禁止静默覆盖。没有external_id时以导入批次身份+行序号+内容摘要去重，只保证同一确认批次的重试幂等；不同文件/批次中“看起来相同”的交易提示可能重复，由用户明确处理，不自动合并合法的同日双买入。手工记账同样持久化requestId与payload摘要。

解析/校验/预览发生在提交事务之外；确认时再次核验数据版本并原子提交业务与导入收据。提交取消/失败回滚整批，重复确认返回持久结果；成功响应必须在事务提交后。导入原文件作为用户数据保留在imports/，可由独立清理动作删除。

### 7.4 持仓与交易

动作：
- fund.db 仅由 fund-host 写；基于标准 data 根路径，SQLite WAL/FK、版本化增量迁移、原子备份。
- 按7.2实现账户与基金基本资料、已确认买入/卖出、期初持仓、交易列表与持仓汇总。
- positions 是可重建投影；交易/明确标记的期初快照是来源。禁止既直接改 positions 又用 transactions 重算造成双权威。
- 同一天同账户同基金可以存在两笔合法买入；不能把 (account, fund, date, type) 当所有交易的唯一键。手工提交以 requestId 幂等；导入以真实外部交易 ID 或已确认导入批次/行身份幂等。
- 已确认交易才改变持仓；待确认记录单独展示，不能以估值净值伪造已确认成交。
- 金额/净值/份额使用十进制定点语义，定义精度和舍入，禁用二进制浮点累计成本；超卖在写入时拒绝。卖出后剩余成本及已实现收益可重放。
- 用户保存返回成功前完成事务；输入草稿与已确认交易分开保存，关闭不会把草稿误作交易。
- 零资产显示空态；缺净值显示缺失/过期，不把成本价当最新市值。

至少保留一组黄金用例：买入 100 份×1.00，费用 1.00；再买入 50 份×1.20，费用 0.50；总成本 161.50、份额 150；卖出 60 份×1.30、费用 0.50，按移动平均成本法扣成本 64.60，已实现收益 12.90，剩余份额 90、成本 96.90。此为测试 fixture，禁止写入用户初始数据。

验收：开户→录入→查看→卖出→重开可用；同日多笔交易、重复提交、超卖、重算、崩溃恢复、精度、未确认交易有有效测试。

### 7.5 导入与净值

动作：
- 按7.3提供两种明确CSV模板和手工补录；只处理用户主动选择/提交的内容，不开放任意路径扫描。
- 导入流程为预览→字段/格式检查→差异与重复项→确认→单事务提交→结果。失败保留原数据，重复导入不倍增持仓。
- 仅有持仓快照时记录带来源/日期的期初快照；不捏造真实买入交易。成本由市值减收益推导时显式标记推算，缺失不默认为零。
- 接入一个验证可用的基金净值 HTTPS 来源；首选审计文档中的 EastMoney Mobile 作为调查起点，实际接口/使用条件和字段以实施时核验为准。不 eval 外部脚本/JSONP。
- 外部来源超时、无数据、限流、字段变化分别处理；有界请求、增量历史净值、缓存/数据库去重；同步由前台或用户动作触发，无后台常驻刷新。
- 每条净值/汇总显示 source、navDate、fetchedAt、是否过期；只有来源可比且数据完整时计算总市值/盈亏。跨日期或缺失项显示覆盖情况，不伪造完整总额。
- 净值不可用仍可使用本地账本和已明确日期的缓存；数据源失败不能吞成空持仓或 0 市值。
- 无公开可用来源时，在线净值验收保持 pending；不能用 fixture 冒充线上可用或把来源缺口藏进“改造完成”。

若另有已确认要求接入养基宝：单独追加认证工作包，先验证 HTTPS/合规可用接口；Token 只进 Keychain，失效为 auth_required，QR 轮询仅可见+有界且可取消。不把审计报告中的历史 HTTP 明文端点直接作为生产默认。

验收：手工与导入均产生真实可持久化资产；重复导入幂等；净值源有真实调用证据与脱敏 fixture；缺失/过期/失败显示正确；业务联网和凭据不经过扩展页面。

### 7.6 数据迁移和关闭

- 内置基金代码随主应用升级；用户基金数据继续使用既有私有目录和 Keychain namespace，不随系统安装包覆盖。
- 首次打开由当前用户权限的基金执行程序完成必要初始化/迁移。迁移前停止写入、获取运行锁、生成包含 WAL 一致性的备份，再迁移和验证。
- 迁移失败且尚未接受新写入时恢复一致性备份，显示明确错误。新版本已写入后，旧代码是否可用必须比较真实 schema 与目标整包的读写范围；不兼容或未知则拒绝回退。
- 重装同版、升级、代码修复不删除用户数据；清除数据和 Keychain 使用独立明确确认。
- 草稿、导入中、保存中、已保存的状态必须区分；关闭/崩溃/重开不丢已提交交易，不把未提交草稿写为成交。
- 开户、两笔买入、卖出、导入、净值、关闭重开和整包更新后保留数据，全部使用真实模块完成。

- 开发只跑最小覆盖检查；疑似测试 hang 先分离编译/执行，检查锁和残留进程，不叠跑、不 pipe tail。
- 性能按同机同构建类型前后比较；整包变大不能掩盖 Core 或常驻资源回归。
- 实装使用明确隔离/可恢复测试环境。修改日常系统或公开发布前，先准备具体候选/hash/作用范围/恢复资料，再复用有效授权或仅对缺失动作取得批准。
- 开发/正式信任隔离、Keychain 所有权、目录限制、正常平台安全机制继续有效。
