# Natives 单一应用、内置模块与完整交付实施方案

> 修订：2026-09-13，依据当前代码、测试、发布记录及最新 AGENTS 复核。
> **唯一产品路线：Natives 是一个完整应用，基金等功能是内置模块，全部随 Natives 一起安装、更新和修复。没有模块独立下载、安装、更新、卸载或 Release。**
> 本版替换本文件此前“独立应用包”“统一套件加二次下载”“条件备选”路线，不并行保留。
> **检查结论：当前应用中心尚不符合预期。规范已部分收敛，生产页面、Host 接口、数据清理和安装包仍保留旧实现，完整产品实操尚未验收。**
> 本轮交付是方案和文档索引，未实施产品代码、系统安装或公开发布。
> P0 清理 ADR/Standards 正文中与已采纳决定冲突的旧条款，不重新讨论产品路线。模块数据、Secret、安全隔离和回收约束继续保留。

**执行顺序：§0–§3 冻结产品与边界 → §4 确定交互 → §5 实施 P0–P6 → §6 打包发布与实操 → §7/§8 完整验收。§10 可直接交给本地 Agent。**

## 0. 本次决定，不再混合两种模式

| 对象 | 本次定义 |
|---|---|
| Natives | 唯一产品、唯一用户安装对象、唯一发布和更新入口 |
| 空间、文件、AI、基金 | Natives 内的功能模块 |
| 应用中心 | 内置模块的入口与偏好管理页，保留现有名称 |
| 基金代码 | 随 Natives 构建并进入完整安装包，不在首次使用时下载 |
| 基金数据 | 用户私有数据，升级/重装/修复保留 |
| Chrome 扩展 | 主应用必需的界面组件，随同一版本交付；用户完成 Chrome 要求的一次本地加载 |
| 更新 | 只提示“更新 Natives”，安装一个锁定所有组件版本的完整产品版本 |
| 修复 | 修复 Natives 安装，或有证据地恢复同一产品版本的受损文件；不重新下载某个模块 |

取消的产品能力：

- 应用中心的“可添加/应用商店”、模块安装/下载进度、模块独立升级、模块卸载。
- 运行时发现任意新 appId，在线 Catalog 驱动新业务，Fund 的独立 nap/Release。
- 自动下载“未随附模块”、把模块首用称为安装、两种生产模式切换开关。
- 独立应用包方案及其备选分支。今后如要重新引入，属于另一次明确产品决策，不在本轮预留平台。

基金源码可以继续按清晰领域边界维护，但用户版本、安装包和 Release 与 Natives 联动。内部使用几个受控程序属于实现细节，不形成可单独安装的产品。

## 1. 最终用户流程

~~~text
下载一份 Natives 安装包
  → 双击安装
  → 安装完成说明给出随包扩展的固定目录和三步加载说明
  → Chrome 开启开发者模式、加载已解压目录
  → 进入扩展的首次配置页，完成一次当前用户的 Natives 配置
  → 空间、文件、AI、应用中心可使用
  → 应用中心点击“基金：打开”
  → 直接使用内置基金，首次仅做必要的数据初始化
~~~

基金初次打开不下载代码，不安装第二个程序，不要求选择基金包、不显示“安装基金”。当前用户的产品配置从已安装的完整产品中校验全部固定模块并完成注册，见 §3.3；必须在报告产品就绪之前完成，不能拖到应用中心或首次打开基金时做。

以后：

- 点击 Chrome 扩展图标/既有产品入口进入 Natives。
- 有新版只出现“更新 Natives”；更新包含主程序、浏览器组件及所有内置模块。
- 模块卡片只负责打开、显示/隐藏、偏好和必要的错误说明。
- 用户隐藏模块不卸载代码；清除模块数据是另一个明确的危险操作。
- 日常不需要源码、Node/npm/Rust、Terminal、npm run dev 或手工 Native Messaging 配置。

遵守当前 AGENTS：不创建 `/Applications/Natives.app`、独立 `.app`、Dock 或 LaunchServices 入口。前版方案中“薄 Natives.app / 双击 Natives.app”的表述撤销。沿用系统源内的薄入口用于短时目录定位和诊断；验收主路径必须通过安装说明和扩展直接走通，不依赖桌面壳或用户执行命令。

Chrome 最终选择包含 manifest.json 的**解压目录**，不能直接选择 ZIP。本地加载和重载遵循实际浏览器步骤，不使用普通 Chrome 的 --load-extension 自动加载。[Chrome 官方加载说明](https://developer.chrome.com/docs/extensions/get-started/tutorial/hello-world)

首发平台按真实证据声明。macOS arm64 与 macOS x64 分别对应 Apple Silicon 与 Intel；未做实机验收的平台不标可用。

## 3. 架构：保留必要分工，取消模块分发系统

### 3.1 一个产品组合

~~~text
Natives 完整安装包 / 唯一产品版本
 ├─ 薄打开入口
 ├─ Chrome 界面组件
 ├─ Files 本机能力
 ├─ Model 本机能力
 └─ 基金内置代码与界面

打开某功能 → 现有受控能力按需工作
关闭页面 → 正确保存/取消并回收资源
更新产品 → 所有组件按同一组合清单切换
~~~

复用现有 Files/Model/Fund 程序和 app-host-support。无需新建聚合 Runtime、modules-host、动态模块加载器、通用 invoke 或另一层后台服务；也无需为了“一个应用”合并各领域数据库。

基金现有 UI 可继续构建期嵌入受控基金执行程序，经现有 app.html 和受限 iframe 展示。它是安装包内固定业务代码，不是应用中心下载的插件。保留 appId=fund、现有页面路由、运行锁和数据目录，避免无意义重命名。

### 3.2 唯一清单与状态权威

复用现有 suite/构建元数据，收敛为一份已签名的产品组合清单：

- 产品版本、平台/架构、固定扩展 ID、兼容协议。
- 每个必需文件的相对路径、长度、最终 hash 和签名身份。
- 内置模块列表及其固定入口、名称、构建版本、数据 schema 兼容范围。
- 组件版本可作为内部构建追踪信息；用户只看到 Natives 产品版本。

清单只描述安装包已包含的固定文件，**没有模块下载 URL、安装脚本、用户自定义入口或运行时添加模块能力**。新模块只能通过新的完整 Natives 版本增加。

权威分工：

| 事实 | 来源 |
|---|---|
| 本产品包含哪些模块/文件 | 当前已验证产品清单 |
| 模块是否可用 | 实际文件/身份/协议与必要只读检查，不由旧 installed=true 推断 |
| 显示在侧栏、是否启用入口 | 复用已有用户偏好记录 |
| 基金数据/迁移状态 | 基金数据域 |
| 当前是否使用中 | 实际 owner/运行锁，作为内部维护依据 |

旧 App Store 表按需要保留用户偏好、历史收据、迁移证据及受控运行所需的固定模块投影，不继续代表可独立安装的远端应用。投影由完整产品配置维护，不新建第二 Registry。

### 3.3 安装与运行边界

- 系统安装器只向 `/Library/Application Support/Natives/` 放薄入口、主 Host、固定扩展文件和**全部固定内置模块文件**；浏览器要求的最小 Native Messaging 注册由同一清单生成。不写用户 DB/activation，不以 root 执行基金迁移。
- 本版统一将 Chrome 实际加载目录定为 `/Library/Application Support/Natives/ChromeExtension/`，包内即为包含 manifest.json 的完整解压目录。它随整包切换，不再同时维护用户扩展副本、文本 current 或首次联网解压链。P0 将此路径写入现有契约；root-owned 固定代码目录与用户数据目录严格区分。
- 薄入口继续复用 `launcher_setup.rs` 的短时打开/定位/诊断能力，并按系统源布局改正路径；不得创建 `.app`、另一个桌面界面或常驻进程。安装完成说明提供可直接复制的真实目录及浏览器操作，不能把执行脚本当普通用户入口。
- **当前用户的产品配置是产品安装的收尾步骤**：扩展首次配置页通过已有主 Host 连接，在明确的“完成 Natives 配置”操作下校验当前完整清单，为全部固定模块准备私有活动载荷、浏览器注册和 activation。复用既有锁、校验、落盘和恢复逻辑，不新增安装数据库。输入不接受模块选择、URL、任意路径、Host 名或执行参数。
- 活动模块程序和数据继续位于 `~/.natives/apps/<appId>/`；系统源中的固定模块文件是完整产品安装内容，不能直接将活动执行程序移到系统源以绕过私有根约束。产品配置从可信本地安装内容完成，**无 nap、无逐模块安装记录、无 seed reconciliation、无应用中心自动补装**。
- 一次产品配置以同一 `productGeneration` 绑定所有模块。全部必需模块和注册验证成功后才标记本用户产品就绪；中断则阻止业务并提示“完成 Natives 配置/修复 Natives”，从同一产品事务恢复。不能部分成功却展示整体可用。
- 模块首用只在当前用户权限下做业务数据初始化/迁移。`apps:list`、应用中心打开和普通模块 `open` 不能隐式补复制代码或写注册；未完成配置应回到产品配置入口。
- 现有 activation 投影保留，但绑定签名产品清单中的固定模块、产品 generation、受控私有路径及调用身份；管理偏好 revision 变化不触发程序重新激活。
- 主 Host/基金模块按页面 Native Port 使用；Model Host 仅在用户已明确开启现有驻留设置时驻留。无通用常驻 Runtime、SW Port/轮询、Login Item/LaunchAgent/Jobs。
- Secret 不进页面；基金库不归 Files/Model 写；iframe 的 sandbox、鉴权、loopback 限额与 EOF 回收保留。
- 开发与正式身份、目录、签名、注册和 Keychain 必须隔离，不能靠改为整包发行绕过平台信任。

### 3.4 列表与操作契约：在现有接口上改，不新建平台

复用 `apps:list`、既有记录/偏好和导航投影。列表是“当前产品固定模块定义 + 该用户偏好 + 已知就绪情况”的读取投影，不依赖 apps 表中有安装记录。

| 返回事实 | 必要字段/含义 |
|---|---|
| 产品 | 产品版本、generation、配置状态（未配置/就绪/需修复/不兼容）及明确错误码 |
| 固定模块 | app_id、来自组合清单的多语言名称/说明、受控路由标识 |
| 用户选择 | 沿用 enabled、show_in_sidebar、sidebar_order；缺省值仅用于从未作出选择的用户 |
| 可用性 | 是否可打开及原因；来自当前产品验证结果，不使用远端候选包兼容性推断 |
| 数据状态 | 只返回已知信息；未检查为 unknown。需要最新业务状态时由当前模块 owner 查询，普通列表不得启动每个模块或打开其业务库 |

字段命名按现有契约统一，以上不要求新建通用状态机/Registry。不得再用 installed、download_url、availablePackages、Catalog 版本决定用户按钮。空旧 apps 表 + 含 fund 的有效产品清单必须产生基金卡片；产品配置未完成时卡片提示产品配置，绝不能显示“安装基金”。

| 操作 | 实施约束 |
|---|---|
| 握手、列表 | 握手失败后停止后续依赖请求；列表不触发下载、seed、注册、数据迁移或自动修复 |
| 打开 | 校验固定模块和产品 generation；优先聚焦当前 profile 的同一模块页，不在其他 profile 搜寻或跨用户接管 |
| 显示/隐藏、历史入口开启 | 仅修改既有偏好和投影；不增删程序/注册，不重启或终止正在打开的模块 |
| 数据清除 | 独立实现 §4.3；禁止路由到 uninstall、remove_activation 或删除模块根目录 |
| 旧模块分发请求 | `apps:suite_prepare`、install_begin/chunk/finish/commit/abort、uninstall、rollback 对当前产品明确不支持，并在任何存储/网络/注册变更前返回稳定错误；复用或定义一个固定协议错误码 |
| 产品配置、更新、修复 | 只在现有产品配置/设置入口执行，固定完整产品输入，复用底层事务；不是页面每次连接后的副作用 |

升级时旧未完成安装事务由产品迁移在锁内按已有 journal 安全收尾，不能为此继续开放旧客户端提交。旧客户端遇到协议变更显示“更新 Natives/重新加载扩展”，不静默回退 Catalog。

去掉“可添加”、推荐市场、安装/下载、单独版本/更新、模块卸载、启动/停止/重启、PID/Host 状态。产品更新统一放现有设置中的“关于/更新 Natives”，不重复出现在各卡片。

### 4.2 状态和行为

| 状态 | 用户看到 | 行为 |
|---|---|---|
| 内置功能可用 | 打开 | 直接进入；已有页面优先回到原页面 |
| 显示在侧栏关闭 | 仍可在中心打开 | 仅改变导航，不下载、不删除、不停止正在使用的页面 |
| 历史记录为停用/已移除 | 入口未开启、开启入口 | 保留旧选择；开启只改偏好，代码已经随产品交付 |
| 首次数据初始化/迁移 | 具体初始化进度 | 无代码下载、无“正在安装基金” |
| 当前用户尚未完成产品配置 | 完成 Natives 配置 | 进入产品配置流程；应用中心不自动写文件、基金按钮不变成安装 |
| 文件损坏/版本不兼容 | 功能暂不可用、查看原因 | 引导“修复 Natives”或“更新 Natives” |
| 数据损坏/迁移失败 | 数据需要处理 | 给出备份/恢复说明；不伪装成安装问题、不自动清库 |

隐藏、停用和清数据不能互相代替。默认不增加新的模块停用功能；只承接旧用户的明确停用/移除意图，用户开启后恢复正常入口。

### 4.3 数据管理

- 查看数据说明与必要占用；未知大小明确未统计，不伪造 0。
- 导出/备份沿用现有能力；清除基金数据与 Keychain 按现有规范二次确认，确认页列出实际范围。默认保留登录凭据，删除凭据必须单独勾选确认。
- 关闭/隐藏入口保留数据。修复、重装、产品升级同样保留。
- 不提供名为“卸载模块”的操作，因为模块代码仍属于整包。

**清数据的具体实现要求：**

1. `apps:clear_data` 与 `apps:uninstall` 分开分发；先验证固定 appId、当前产品、确认范围、幂等 requestId 和 caller，再持有既有操作/运行锁。业务仍在使用时提示保存关闭，不强制结束或边写边删。
2. 只处理该模块的数据目录及用户明确选择的 imports/cache/日志/Keychain namespace。每个目标做既有路径与链接边界校验，禁止递归删除 `apps/<appId>/` 整体。
3. 保留程序文件、签名记录、权限、Native 注册、activation、产品清单/generation、显示/启用/排序偏好；不写 removed 意图、不删固定模块身份。
4. 复用持久清理收据/journal，存放在本次清理范围外，明确区分数据重置与历史卸载收据。失败显示 cleanup_pending、具体未完成范围并允许同一确认操作重试；完成的 requestId 重放只返回原结果，不能把后来录入的新数据再清一次。
5. 清理未完成时暂不开放该模块写入；成功后数据状态为空，重新打开由模块正常初始化。其他模块的数据与凭据不动。

验证必须比较清理前后代码 hash、注册、activation 和偏好；仅断言 DB 不存在不够。导出备份到模块范围之外的用户文件，不被此次清除连带删除。

### 4.4 外观与状态同步

- 独立应用中心、设置内嵌中心和 app.html 复用产品管理面外观偏好；空间 Widget 使用空间局部规范。
- 查明当前生产主题协调器，统一 dark/light 和历史别名映射，删除重复监听，不建立另一 localStorage/chrome.storage 权威。
- 使用 extension 当前 CSS tokens、图标和弹窗；不恢复历史 src/Tauri 组件。
- 中英文、字号层级、焦点、禁用态、错误和小窗口可访问；主题切换不会重启基金。
- sidebar/偏好/失败通知只更新相关展示；bfcache 恢复所需监听与握手，撤销旧 token。
- 不在普通 UI 暴露内部进程和调试字段。

### P0：同步唯一产品决策

AGENTS、ADR 修订头和部分产品规范已经采纳本次决定。先检查并消除仍冲突的正文：ADR-0027/0029、technical/06 的 R-APP-01/09/17、契约、发布门槛和索引；只改实际冲突处，不重复写另一套规范：

- 正式发布授权、签名/公证要求继续生效。

交付：规范一致，默认代码和发行产物只有一种产品模式。

### P1：一个构建入口、一个安装布局

- installers/macos/build-pkg.sh 是唯一系统安装引擎；installer-package.mjs 只组装输入/调用，移除重复 pkgbuild 和第二布局。
- 主程序、扩展、基金及支持库使用锁定的源码与依赖，生成同一组合清单；不能把开发机 ../ 路径当用户或 CI 环境要求。

- Fund 可复用相邻项目，候选记录其源码归档 hash/commit 和依赖锁；不重建项目、不新建远端仓库。

- 主/模块 Native Messaging manifest 全由产品布局生成。解包后逐个验证实际可执行路径、文件身份、架构和 origin。
- 产品清单/包验证替代独立模块 Catalog/nap 发布校验，不为基金再维护另一套发布工作流。
- 删除产品入口对本地源码、target/debug、dev server 和试验目录的依赖。

交付：完整组合候选；修复 D02/D03，不另写一个安装系统。

### P2：内置模块读取与旧数据迁移

- 在 `launcher_setup/app_store` 的既有职责内落实 §3.3 当前用户完整配置：只读取已验证系统源，为本用户配置全量固定模块，绑定同一产品 generation，幂等恢复后才就绪。扩展通过既有产品配置页触发，不从应用中心触发。
- apps.js/native-app-client/App Store 查询和导航投影按 §3.4 改造；无远端发现依赖。空 apps 表也返回产品声明的基金；未知可用性不伪装可用或未安装。
- 删除页面对 Catalog/package-transfer/prepareSuite 的调用；握手不兼容后不再 list 或写入。旧生产 suite_prepare/install/chunk/rollback/uninstall 明确拒绝，包含直接调用 Host 的反例，不能只隐藏按钮。
- 复用安装校验、文件限制、身份函数和恢复工具，在**产品安装/更新**层使用；避免以删除旧路由为由删掉安全能力。
- `clear_data` 按 §4.3 拆离 uninstall；审计其所有调用者、历史 retained-data 入口和失败重试，防止任一路径继续移除固定程序/偏好。历史真正卸载收据只允许在受控产品迁移中收尾。

- 旧程序/注册/缓存只按精确归属、版本与收据清理；用户数据不动。迁移失败保留 journal 和修复说明。
- 切换后只激活固定产品程序；旧动态注册不能作为静默 fallback 继续运行。

交付：新用户完成一次产品配置后直接打开基金；旧用户数据和选择不丢。清数据后代码/注册/偏好仍在；应用中心读取不发起任何安装事务。

### P3：扩展准备和主入口

- 主 Launcher 复用已有 CLI/平台打开能力，固定安装源；不新增常驻服务、另一更新器或业务 UI。
- 按 §3.3 随包放置固定**真实目录** `/Library/Application Support/Natives/ChromeExtension/`，安装完成说明直接给出此路径。去掉生产用户副本/current 文本准备链，不制造先运行 Launcher 才能拿到扩展、却又没有合法 Launcher 入口的循环依赖。
- 构建输入 ZIP 由同一产品清单精确绑定文件名/长度/hash/版本/固定公钥 ID；不能任取 SHA256SUMS 首行。将现有有界校验用于包组装，最终还要核验解包后的扩展逐文件内容。
- 解压到候选 staging，拒绝路径穿越、越界链接、重复冲突条目、超限和错 manifest。相同版本同 hash 幂等；整包验证与维护条件满足前不能删除正在加载的目录。

- 旧 handshake 文件只代表历史记录；目录存在不等于当前 profile 加载/启用，错误 profile/缺 Chrome/版本不兼容真实显示。
- Native 主程序路径与打包目录完全一致，读取系统源失败不回退当前工作目录。

交付：用户按安装说明加载随包目录即可进入产品配置，无源码、终端或第二下载。旧用户的旧扩展路径给出一次明确换载说明并验证 ID/版本；不悄悄维持两个自动更新目录。

### P5：整包更新、修复与恢复

- 只有产品级“检查更新/更新 Natives”；来源为可信完整产品 Release，按已有设置和前台动作触发，无后台轮询。

- 当前及其他用户在更新后进入产品时，先由兼容的前台配置页完成本用户整包 generation 更新并恢复固定模块投影，再开放业务；不由 root 改用户库。该过程不在应用中心或基金 open 隐式发生，没有用户扩展副本同步链。
- 基金数据迁移在该用户首次打开时进行；旧代码回退前比较实际 schema 与目标完整版本，不能用旧备份覆盖新写入。
- 主产品修复使用当前或兼容的完整发行包恢复代码/注册/扩展，不重置个人数据，不暗中下载 fund.nap。
- 修复失败保留真实错误与恢复信息，不能写“已是最新/修复成功”。

交付：同一组合版本的一致性与用户数据有真实故障切点证据。

先完成五个能判断方向是否正确的检查：**中心加载 Catalog/prepareSuite 次数均为 0；空安装表仍显示内置基金；旧分发方法写入前拒绝；清数据保留代码/注册/偏好；实际整包包含真实基金且注册路径有效。** 然后继续完整 A/B、业务、主题、更新与发布验收。这是依赖顺序，不是只交付五项的 MVP。

### 6.3 必须做一次的真实用户操作

在干净测试用户/机器执行，不能使用源码目录、开发 Host、旧扩展或本地缓存冒充：

1. 从公开 Release 下载完整 Natives 包并正常系统安装。
2. 按安装完成说明加载 `/Library/Application Support/Natives/ChromeExtension/`；在扩展前台完成当前用户产品配置，实际 ID/版本/握手和全量模块就绪状态正确。全程不执行命令、不依赖 `.app` 壳。
3. 打开空间、文件、设置、应用中心；关 Chrome 后重开仍可用。
4. **断网打开基金并录入/保存本地账本**：无任何模块代码下载，数据可重开；在线净值另验真实来源。
5. 隐藏基金侧栏入口，再从中心打开；历史停用者手动开启后可用，均没有安装步骤。
6. 实际重启测试 macOS，重新打开，原配置/数据保留。
7. 发布并取得完整 Natives N+1，执行整包升级；主程序、扩展及基金属于同一组合，基金真实 UI/业务变化，数据保持。
8. 在隔离环境破坏安装文件，运行主产品修复；数据不清除、失败不假成功。
9. 测试迁移失败/不兼容回退、同版重装、旧用户数据迁移及多 profile 使用。

仅新建 Chrome profile 不代表干净系统，还必须核验 OS Native Host 注册、运行进程、用户目录与 Keychain 的隔离。不得在用户日常数据上人为破坏文件或重启机器做实验。

## 7. 基金内置模块的业务验收

### 7.1 本次范围

本阶段目标为随 Natives 完整交付的基金内置模块：账户、基金、持仓、确认交易、手工/文件导入、净值和基础市值/盈亏展示，以及完整的数据与生命周期保护。

现有审计报告中的养基宝登录、跨市场行情、穿透估值、FundScore、风险分析与 AI 解释，不自动全部纳入本次模块整改。不得做成假入口。P0 用“本次交付/后续候选”矩阵记录；若用户已有其他已确认基金需求，补入矩阵并实现相应工作包，不能被本方案静默删减。

当前相邻基金仓库已有业务和 UI 源码；其完整性须在 P0 重新核验。本轮只审计应用中心，不将已有源码视为基金验收通过，也不按早期“没有实现”的描述重建工程。

### 7.2 首版资金与记账口径

- 只处理人民币场外基金的已确认交易；币种固定CNY。股票/外汇/多币种、场内买卖、自动交易不在本次范围。
- amount、fee、cost_basis、realized_pnl以元为单位，输入最多两位小数；quantity与基金NAV/price最多四位。多余有效精度不静默截断，返回校验错误。
- 内部采用有界十进制数及溢出检查；截取到指定精度统一向零截断（ROUND_DOWN），不是二进制浮点或负数floor。中间乘除不提前量化，落账的金额/费用/成本分配量化到两位，持仓份额四位。
- amount表示不含费用的已确认成交金额；BUY计入成本amount+fee，SELL净收入amount-fee。未提供amount时由quantity×price截取两位生成；提供时与该值差异超过0.01元即作为冲突进入导入预览/人工更正，不能悄悄改账。金额和份额必须正，费用非负，卖出费用不得大于成交金额。
- 卖出使用移动平均成本：扣除成本=当前成本×卖出份额/当前份额，最终截取两位；已实现收益=卖出净收入-扣除成本。全部清仓时扣完剩余全部成本，避免分钱残留；任何时间点按稳定顺序（交易日期、确认时间、内部ID）重放结果一致。
- 平均持仓成本价与展示NAV可显示四位，但已四位显示的均价不能回写成本计算。缺成本的期初记录保持cost_basis=null，相关收益显示不可计算；不得补零后产生假利润。
- 交易日期按Asia/Shanghai的YYYY-MM-DD解释；净值日期按数据源原值保存，节假日/缓存不改写成今天。卖出超过重放所得可用份额直接拒绝。
- 本节黄金用例必须作为精确断言；另覆盖分币成本、负收益、全部清仓、溢出和同日多笔顺序。

### 7.3 CSV模板与导入身份

首版只支持UTF-8 CSV（可有BOM，标准双引号转义），不承诺XLSX。文件≤5MiB、数据行≤20,000、单字段≤4KiB；界面选择模板版本1，不通过任意脚本/表达式映射列。传输复用应用业务HTTP的分块上传，每块≤256KiB，预览分页，不突破通用请求上限。

| 模板 | 必填列 | 可选列/规则 |
|---|---|---|
| 已确认交易 | account,fund_code,trade_date,type,quantity,price | amount,fee,external_id；type为BUY/SELL；fee缺省为0，amount按7.2计算 |
| 期初持仓快照 | account,fund_code,as_of,quantity | cost_amount,market_value,earnings,nav,nav_date,external_id；成本缺失时允许以市值减收益推算但必须标记，结果为负需人工更正；无法推算则保留未知成本 |

account映射到本地唯一账户，缺失账户先在预览中确认创建；fund_code为六位数字字符串，保留前导零。快照仅用于尚无该账户/基金记账历史的期初建账；已有流水时返回冲突，不覆写positions或编造反向交易。

持久化import_runs：sourceId、templateVersion、原文件SHA-256、导入参数/账户映射摘要、确认requestId、状态和结果；行记录保留原行序号、规范化字段摘要和结果。精确重复（同source/template/rawHash/参数）返回原结果，不再次入账；同requestId不同payload摘要返回conflict。

有可信external_id时以(sourceId,accountId,external_id)去重；相同ID内容变化进入冲突预览，禁止静默覆盖。没有external_id时以导入批次身份+行序号+内容摘要去重，只保证同一确认批次的重试幂等；不同文件/批次中“看起来相同”的交易提示可能重复，由用户明确处理，不自动合并合法的同日双买入。手工记账同样持久化requestId与payload摘要。

解析/校验/预览发生在提交事务之外；确认时再次核验数据版本并原子提交业务与导入收据。提交取消/失败回滚整批，重复确认返回持久结果；成功响应必须在事务提交后。导入原文件作为用户数据保留在imports/，可由独立清理动作删除。

### 7.4 持仓与交易

动作：
- fund.db 仅由 fund-host 写；基于标准 data 根路径，SQLite WAL/FK、版本化增量迁移、原子备份。
- 按7.2实现账户与基金基本资料、已确认买入/卖出、期初持仓、交易列表与持仓汇总。
- positions 是可重建投影；交易/明确标记的期初快照是来源。禁止既直接改 positions 又用 transactions 重算造成双权威。
- 同一天同账户同基金可以存在两笔合法买入；不能把 (account, fund, date, type) 当所有交易的唯一键。手工提交以 requestId 幂等；导入以真实外部交易 ID 或已确认导入批次/行身份幂等。
- 已确认交易才改变持仓；待确认记录单独展示，不能以估值净值伪造已确认成交。
- 金额/净值/份额使用十进制定点语义，定义精度和舍入，禁用二进制浮点累计成本；超卖在写入时拒绝。卖出后剩余成本及已实现收益可重放。
- 用户保存返回成功前完成事务；输入草稿与已确认交易分开保存，关闭不会把草稿误作交易。
- 零资产显示空态；缺净值显示缺失/过期，不把成本价当最新市值。

至少保留一组黄金用例：买入 100 份×1.00，费用 1.00；再买入 50 份×1.20，费用 0.50；总成本 161.50、份额 150；卖出 60 份×1.30、费用 0.50，按移动平均成本法扣成本 64.60，已实现收益 12.90，剩余份额 90、成本 96.90。此为测试 fixture，禁止写入用户初始数据。

验收：开户→录入→查看→卖出→重开可用；同日多笔交易、重复提交、超卖、重算、崩溃恢复、精度、未确认交易有有效测试。

### 7.5 导入与净值

动作：
- 按7.3提供两种明确CSV模板和手工补录；只处理用户主动选择/提交的内容，不开放任意路径扫描。
- 导入流程为预览→字段/格式检查→差异与重复项→确认→单事务提交→结果。失败保留原数据，重复导入不倍增持仓。
- 仅有持仓快照时记录带来源/日期的期初快照；不捏造真实买入交易。成本由市值减收益推导时显式标记推算，缺失不默认为零。
- 接入一个验证可用的基金净值 HTTPS 来源；首选审计文档中的 EastMoney Mobile 作为调查起点，实际接口/使用条件和字段以实施时核验为准。不 eval 外部脚本/JSONP。
- 外部来源超时、无数据、限流、字段变化分别处理；有界请求、增量历史净值、缓存/数据库去重；同步由前台或用户动作触发，无后台常驻刷新。
- 每条净值/汇总显示 source、navDate、fetchedAt、是否过期；只有来源可比且数据完整时计算总市值/盈亏。跨日期或缺失项显示覆盖情况，不伪造完整总额。
- 净值不可用仍可使用本地账本和已明确日期的缓存；数据源失败不能吞成空持仓或 0 市值。
- 无公开可用来源时，在线净值验收保持 pending；不能用 fixture 冒充线上可用或把来源缺口藏进“改造完成”。

若另有已确认要求接入养基宝：单独追加认证工作包，先验证 HTTPS/合规可用接口；Token 只进 Keychain，失效为 auth_required，QR 轮询仅可见+有界且可取消。不把审计报告中的历史 HTTP 明文端点直接作为生产默认。

验收：手工与导入均产生真实可持久化资产；重复导入幂等；净值源有真实调用证据与脱敏 fixture；缺失/过期/失败显示正确；业务联网和凭据不经过扩展页面。

### 7.6 数据迁移和关闭

- 内置基金代码随主应用升级；用户基金数据继续使用既有私有目录和 Keychain namespace，不随系统安装包覆盖。
- 首次打开由当前用户权限的基金执行程序完成必要初始化/迁移。迁移前停止写入、获取运行锁、生成包含 WAL 一致性的备份，再迁移和验证。
- 迁移失败且尚未接受新写入时恢复一致性备份，显示明确错误。新版本已写入后，旧代码是否可用必须比较真实 schema 与目标整包的读写范围；不兼容或未知则拒绝回退。
- 重装同版、升级、代码修复不删除用户数据；清除数据和 Keychain 使用独立明确确认。
- 草稿、导入中、保存中、已保存的状态必须区分；关闭/崩溃/重开不丢已提交交易，不把未提交草稿写为成交。
- 开户、两笔买入、卖出、导入、净值、关闭重开和整包更新后保留数据，全部使用真实模块完成。

| T17 真实基金 | §7 账户、买卖、重放、CSV、净值与错误 | 黄金数值和幂等正确；真实持久化/来源，不以空壳通过 |
| T18 整包升级 | 同一用户/profile N→N+1，基金有真实 UI/行为变化 | 全组件属于同一组合；实际扩展重载版本正确，数据/偏好保留 |
| T19 更新故障 | 系统文件/扩展、用户载荷、注册、productGeneration 各切点失败或进程退出 | 恢复一致版本或明确待恢复；未完成全量用户配置不宣告就绪，不让新 Host 混旧模块继续业务 |

| T21 修复与重装 | 破坏隔离安装文件、修复、同版/旧版重装 | 恢复完整产品、数据不变；修复失败不报已是最新，拒绝隐式降级 |
| T22 清数据/重启 | 二次确认，保留/删除凭据两种选择；清理失败、同 requestId 重试、清后写新数据再重放；重启 | 仅清确认范围；代码 hash/注册/activation/偏好不变，模块可直接打开；重放不删新数据；其他模块/备份/Keychain 不误删 |

### 8.2 原门槛的替代规则

P0 完成剩余规范与测试映射；保留已生效的门槛：

- 原 A-G1/B-G5 的“独立 appId/独立更新”改为 T01/T18/T19 的单一组合、完整升级和恢复，不再要求另发基金。
- 完整候选中的真实内置基金先通过 A-Local，才进入 B0–B3；B-Local 通过才称本机可用。现有独立样例测试只服务共享底层规则，不替代这一前置。
- 供应链、路径/注册、数据、Secret、生命周期、竞争、UI、资源、真实业务/数值/净值来源、平台签名与实装门槛全部保留，映射到上表。
- 本地工程通过与正式产品发布实操仍分开；不能删除反例或用 mock 代替真实检查。Core 预算按 2026-09-13 用户决定上调 20% 至 360 KiB（ADR-0024 修订），此后漂移归因纪律不变，不再放宽。

### 8.3 什么才算本轮完成

**完整完成 = 单一产品代码与规范一致 + 全部内置业务验收 + 完整候选通过 + 正式信任/平台门槛通过 + 真实 Release 发布后回下载实操通过。**

- 只有源码、构建、单测、开发服务或本地 pkg 成功，都只能报告阶段结果。
- 缺发布授权/签名身份/某平台机器时，记录具体 pending 和受影响项；其余独立工作继续，不虚构通过。
- 未验证平台不宣传支持；不在已公开产品里自动下载另一未经验证模块补齐。
- 在本文、PR 和已有 CI artifact 中记录证据，不再创建平行方案或多份“最终完成报告”。

证据最少包含：源代码/工作区指纹、构建模式、平台/浏览器版本、完整产品及组件最终 hash、命令退出码、关键 UI/数据/资源证据、发布 URL 与公开回下载摘要。

## 9. 工程执行纪律

- 先读 docs/README、Standards 和当前实际代码，按 P0 修订与本次明确决定冲突的规范。更改 MUST 要有 ADR，不能只删测试。
- 复用现有源码、数据、安装校验、支持库、偏好、tokens 和测试；不重建基金、不新增通用运行时。
- 保留其他任务的工作区修改，不混入无关格式化/重命名/清理。
- 使用 rtk。Cargo 从 Natives 主 checkout 根移除环境 target override，使用唯一 target；不 cargo clean、不建其他 target。
- 开发只跑最小覆盖检查；疑似测试 hang 先分离编译/执行，检查锁和残留进程，不叠跑、不 pipe tail。
- 性能按同机同构建类型前后比较；整包变大不能掩盖 Core 或常驻资源回归。
- 实装使用明确隔离/可恢复测试环境。修改日常系统或公开发布前，先准备具体候选/hash/作用范围/恢复资料，再复用有效授权或仅对缺失动作取得批准。
- 开发/正式信任隔离、Keychain 所有权、目录限制、正常平台安全机制继续有效。

现有验证入口先按新产品语义修正，再运行：

~~~sh
rtk npm run apps:check
rtk npm run apps:integration
rtk npm run apps:browser
rtk npm run apps:chrome-native
rtk npm run apps:e2e
rtk env -u CARGO_TARGET_DIR cargo test -p native-file-host app_store
~~~

apps:e2e 的直连进程只能证明 Native/HTTP 集成，不能因命令叫 e2e 就当普通 Chrome 实操。模块分发的过时测试在 P0 映射为产品安装/升级反例，不能无说明整批删除。

最终产品代码集成必做适用检查一次：

~~~sh
rtk npm run extension:check
rtk npm run perf:check
rtk npm run perf:files
rtk env -u CARGO_TARGET_DIR cargo fmt --check
rtk env -u CARGO_TARGET_DIR cargo test --workspace
~~~

perf:check 已包含的项目保留一次完整结果，不机械叠跑。另做实际候选扫描、真实浏览器/pkg、基金 format/test/build 和业务迁移检查。

本机 Fund Rust 从 Natives 根使用 --manifest-path ../Natives-App-Fund/Cargo.toml，先 metadata 核验 target_directory 沿用主 checkout；独立 CI 锁定源码输入，不依赖开发机相邻路径。

本轮修改仅限 Markdown；已执行的只读审计检查及其限制见 §2.2。文档修改后检查链接、章节、验收覆盖和 diff，不重复运行已通过且代码未变的产品检查。
